# 控制指令扩展实施计划

## 1. 概述

### 1.1 背景

当前控制协议仅支持 4 种命令（`register`/`ping`/`tunnel_update`/`tunnel_push`），服务端对客户端的运行时状态（串口连接、VPN 进程、隧道后端健康等）完全不可见，也无法远程控制客户端侧的隧道生命周期。本计划新增 6 个控制指令，补齐运维可见性和远程控制能力。

### 1.2 纳入范围

| # | 指令 | 方向 | 优先级 | 说明 |
|---|------|------|--------|------|
| 1 | `tunnel_status` | C→S | P0 | 客户端上报隧道运行时状态 |
| 2 | `tunnel_action` | S→C | P1 | 服务端远程启停/重启隧道 |
| 3 | `health_check` | S→C | P1 | 服务端请求客户端探测后端连通性 |
| 4 | `sysinfo` | C→S | P2 | 客户端上报系统信息 |
| 5 | 增强 `ping` | 双向 | P2 | 携带时间戳，测量 RTT |
| 6 | `restart` | S→C | P3 | 服务端请求客户端优雅重启 |

### 1.3 排除范围

- `event`（C→S 事件推送）：需要服务端事件总线和管理后台告警 UI，涉及面广，独立计划。
- `log_subscribe`（S→C 日志流）：需要长期 smux stream 持有 + 流量控制，复杂度高，独立计划。

## 2. 协议设计

### 2.1 通用约定

- 所有命令通过 smux stream 传输，格式：单行 JSON + `\n` 终止
- 客户端发起的命令（C→S）复用现有 `protocol.ControlCmd` 结构扩展字段
- 服务端发起的命令（S→C）复用现有 `tunnel_push` 的推送模式（`OpenStream` → 写 → 读响应）
- 响应格式复用 `ControlResponse{Cmd, Msg, Data}`，新增 `Data` 字段携带结构化数据

### 2.2 指令详细设计

#### 2.2.1 tunnel_status（C→S）

**触发时机**：客户端在以下时机主动上报：
- 每次收到 `tunnel_push` 并应用配置后（配置变更后状态可能改变）
- 定时上报（默认 60 秒，可配置）
- 隧道状态发生显著变化时（串口断开/重连、VPN 进程崩溃/重启）

**请求格式**：
```json
{
  "cmd": "tunnel_status",
  "node_id": "abc12345",
  "statuses": [
    {
      "name": "web-app",
      "type": "http",
      "running": true,
      "connected": true,
      "error": ""
    },
    {
      "name": "serial-mqtt",
      "type": "ser2mq",
      "running": true,
      "connected": true,
      "serial_port": "/dev/ttyUSB0",
      "serial_open": true,
      "mqtt_connected": true,
      "bytes_in": 1048576,
      "bytes_out": 2097152,
      "error": ""
    },
    {
      "name": "vpn-office",
      "type": "vpn-manager",
      "running": true,
      "connected": true,
      "pid": 12345,
      "uptime_seconds": 9000,
      "error": ""
    },
    {
      "name": "tcp-db",
      "type": "ser2tcp",
      "running": true,
      "serial_open": true,
      "clients": 3,
      "bytes_in": 512,
      "bytes_out": 1024,
      "error": ""
    }
  ]
}
```

**响应格式**：
```json
{"cmd": "ok", "msg": "status received"}
```

**类型特定字段**：
| 隧道类型 | 额外字段 |
|---------|---------|
| http/tcp/udp | `connected`(bool) |
| ser2mq | `serial_open`, `mqtt_connected`, `bytes_in`, `bytes_out` |
| ser2tcp/ser2udp | `serial_open`, `clients`, `mode`(server/client), `bytes_in`, `bytes_out` |
| vpn-manager | `pid`, `uptime_seconds` |

**服务端处理**：
- 存储到 `ShardedNodeManager` 的节点扩展数据中（新增 `Node.ClientStatus` 字段）
- 通过 `TunnelInfo` API 暴露给管理后台
- 不触发路由索引重建或持久化

#### 2.2.2 tunnel_action（S→C）

**触发时机**：REST API 收到隧道动作请求时（扩展 `/api/v1/tunnels/:name` 路由）

**请求格式**：
```json
{
  "cmd": "tunnel_action",
  "name": "vpn-office",
  "action": "start"
}
```

`action` 取值：`start` | `stop` | `restart`

**响应格式**：
```json
{"cmd": "ok", "msg": "started"}
```
或
```json
{"cmd": "err", "msg": "tunnel not found"}
```

**客户端处理**：
- 查找 `name` 对应的隧道，按 `action` 调用对应 Manager 方法
- `start`/`stop` 仅对支持生命周期的隧道类型有效（vpn-manager、ser2mq、ser2tcp、ser2udp）
- 对于 http/tcp/udp 隧道返回 `"action not supported for type: http"`

**服务端新增 API**：
```
POST /api/v1/tunnels/{name}/action  {"action": "start|stop|restart", "node_id": "abc12345"}
```

#### 2.2.3 health_check（S→C）

**触发时机**：
- 管理后台手动触发（API 调用）
- 未来可扩展为定时自动探测

**请求格式**：
```json
{
  "cmd": "health_check",
  "name": "web-app"
}
```

**响应格式**：
```json
{
  "cmd": "ok",
  "msg": "",
  "data": {
    "name": "web-app",
    "type": "http",
    "target": "127.0.0.1:8080",
    "alive": true,
    "latency_ms": 12,
    "error": ""
  }
}
```

**客户端处理**：
- http/https：尝试 TCP 拨号到 target，记录连接耗时
- tcp：TCP 拨号到 target
- udp：发送空包到 target（UDP 无连接，仅测试可达性）
- ser2mq：检查串口是否打开 + MQTT 是否连接
- vpn-manager：检查进程是否运行
- ser2tcp/ser2udp：检查串口是否打开

**服务端新增 API**：
```
POST /api/v1/tunnels/{name}/health  {"node_id": "abc12345"}
```

#### 2.2.4 sysinfo（C→S）

**触发时机**：
- 注册成功后立即上报一次
- 每次 ping 间隔周期上报（复用心跳流，不额外开 stream）
- 未来可按需查询（S→C `sysinfo_request`）

**请求格式**：
```json
{
  "cmd": "sysinfo",
  "node_id": "abc12345",
  "os": "linux/arm64",
  "hostname": "gateway-01",
  "uptime_seconds": 258900,
  "go_version": "go1.25",
  "agent_version": "1.2.0",
  "num_cpu": 4,
  "mem_total_mb": 1024,
  "mem_used_mb": 512
}
```

**响应格式**：
```json
{"cmd": "ok", "msg": "sysinfo received"}
```

**服务端处理**：
- 存储到 `Node.SysInfo` 字段（不持久化，重启后客户端重新上报）
- 通过 `GET /api/v1/nodes/{id}` 暴露

#### 2.2.5 增强 ping（双向）

**现状**：`ping` 不携带时间戳，无法测量 RTT。

**改造**：扩展 `ControlCmd` 增加 `ts` 字段：

客户端发送：
```json
{"cmd": "ping", "ts": 1715241600000}
```

服务端响应：
```json
{"cmd": "pong", "ts": 1715241600000}
```

- 客户端发送时记录 `ts`（Unix 毫秒）
- 服务端原样回传 `ts`
- 客户端收到 `pong` 后用 `当前时间 - ts` 计算 RTT
- 服务端在 `handleStream` 中更新 `LastHeartbeat` 时额外记录 RTT 到节点数据

**兼容性**：
- 旧客户端不发 `ts` → 服务端 `pong` 中 `ts` 为 0 → 双方忽略 RTT
- 旧服务端不回传 `ts` → 客户端检测 `ts == 0` → 跳过 RTT 计算

#### 2.2.6 restart（S→C）

**触发时机**：管理员通过 REST API 触发

**请求格式**：
```json
{
  "cmd": "restart",
  "delay_seconds": 5,
  "reason": "version upgrade"
}
```

**响应格式**：
```json
{"cmd": "ok", "msg": "restarting in 5s"}
```

**客户端处理**：
- 响应 `ok` 后等待 `delay_seconds`
- 优雅关闭所有隧道 → 断开 smux 会话 → 退出进程
- 依赖外部进程管理器（systemd/supervisor）自动重启
- 客户端不自行 exec，避免状态泄漏

**服务端新增 API**：
```
POST /api/v1/nodes/{id}/restart  {"delay_seconds": 5}
```

## 3. 实施阶段

### Phase 1：协议扩展（客户端 + 服务端）

**目标**：扩展 `ControlCmd`/`ControlResponse` 结构，支持新指令的基础收发。

**涉及文件**：

| 侧 | 文件 | 变更 |
|-----|------|------|
| 客户端 | `internal/protocol/types.go` | `ControlCmd` 增加 `Ts`/`Action`/`Statuses`/`SysInfo` 字段；`ControlResponse` 增加 `Data` 字段 |
| 服务端 | `internal/tunnel/control.go` | `ControlCmd`/`ControlResponse` 增加同上字段；`handleStream` switch 增加新 case |

**验收**：
- `go vet ./...` 通过
- 现有功能不受影响（新字段均为 `omitempty`）

### Phase 2：tunnel_status + sysinfo + 增强 ping（P0/P2）

**目标**：补齐客户端→服务端的状态可见性。

**步骤**：

1. **增强 ping**（最简单，验证协议扩展是否正确）
   - 客户端：`sendPing()` 中添加 `ts` 字段，收到 `pong` 后计算 RTT
   - 服务端：`handleStream` 中 `pong` 回传 `ts`，记录 RTT 到节点数据
   - 新增 `Node.RTT` 字段（int64，毫秒）

2. **sysinfo**
   - 客户端：新增 `reportSysInfo()` 方法，注册成功后调用；在心跳周期中附带 sysinfo
   - 服务端：`handleStream` 增加 `sysinfo` case，更新 `Node.SysInfo`
   - `core/domain.go`：`Node` 增加 `SysInfo` 结构体字段

3. **tunnel_status**
   - 客户端：新增 `reportTunnelStatus()` 方法，收集各 Manager 状态后发送
   - 各 Manager 暴露 `Status()` 方法（大部分已有）
   - 服务端：`handleStream` 增加 `tunnel_status` case，更新 `Node.ClientStatuses`
   - `core/domain.go`：`Node` 增加 `ClientStatuses` 字段
   - API 暴露：`TunnelHandler.List` 和 `Usage` 中包含客户端状态

**验收**：
- `ping` 增强后旧客户端/服务端仍可正常工作
- `GET /api/v1/nodes/{id}` 返回 sysinfo 数据
- `GET /api/v1/tunnels/usage` 返回客户端侧状态（serial_open、mqtt_connected 等）

### Phase 3：tunnel_action + health_check（P1）

**目标**：服务端获得远程控制和主动探测能力。

**步骤**：

1. **tunnel_action**
   - 服务端：`ControlServer` 新增 `SendTunnelAction()` 方法（类似 `PushTunnelUpdate`）
   - `TunnelConfigService` 新增 `TriggerTunnelAction()` 方法
   - API 新增：`POST /api/v1/tunnels/{name}/action`
   - 客户端：`dispatchStream` 增加 `tunnel_action` 分支，按 action 调用 Manager

2. **health_check**
   - 服务端：`ControlServer` 新增 `SendHealthCheck()` 方法
   - API 新增：`POST /api/v1/tunnels/{name}/health`
   - 客户端：新增 `handleHealthCheck()` 方法，按隧道类型探测后端

**验收**：
- `POST /api/v1/tunnels/vpn-office/action {"action":"stop"}` 可远程停止 VPN 进程
- `POST /api/v1/tunnels/web-app/health` 返回后端连通性和延迟

### Phase 4：restart（P3）

**目标**：远程重启能力。

**步骤**：
- 服务端：`ControlServer` 新增 `SendRestart()` 方法
- API 新增：`POST /api/v1/nodes/{id}/restart`
- 客户端：`handleStream` 增加 `restart` 分支，优雅关闭后退出

**验收**：
- `POST /api/v1/nodes/abc12345/restart` 触发客户端在延迟后优雅退出
- 进程管理器自动重启后节点重新注册

## 4. 数据结构变更

### 4.1 共享协议结构扩展

```go
// ControlCmd 控制命令（客户端和服务端共用）
type ControlCmd struct {
    Cmd      string          `json:"cmd"`
    NodeID   string          `json:"node_id,omitempty"`
    Name     string          `json:"name,omitempty"`
    Token    string          `json:"token,omitempty"`
    Tunnels  []Tunnel        `json:"tunnels,omitempty"`
    Ts       int64           `json:"ts,omitempty"`       // Unix 毫秒时间戳（ping RTT）
    Action   string          `json:"action,omitempty"`   // start/stop/restart（tunnel_action）
    Statuses []TunnelStatus  `json:"statuses,omitempty"` // 隧道状态列表（tunnel_status）
    SysInfo  *SysInfo        `json:"sysinfo,omitempty"`  // 系统信息
    Delay    int             `json:"delay_seconds,omitempty"` // 延迟秒数（restart）
    Reason   string          `json:"reason,omitempty"`   // 原因说明（restart）
}

// ControlResponse 控制响应
type ControlResponse struct {
    Cmd  string          `json:"cmd"`
    Msg  string          `json:"msg,omitempty"`
    Ts   int64           `json:"ts,omitempty"`  // 原样回传（ping RTT）
    Data json.RawMessage `json:"data,omitempty"` // 结构化数据（health_check 结果等）
}
```

### 4.2 服务端 Node 扩展

```go
// Node.SysInfo 系统信息（不持久化）
type SysInfo struct {
    OS           string `json:"os,omitempty"`
    Hostname     string `json:"hostname,omitempty"`
    Uptime       int64  `json:"uptime_seconds,omitempty"`
    GoVersion    string `json:"go_version,omitempty"`
    AgentVersion string `json:"agent_version,omitempty"`
    NumCPU       int    `json:"num_cpu,omitempty"`
    MemTotalMB   int64  `json:"mem_total_mb,omitempty"`
    MemUsedMB    int64  `json:"mem_used_mb,omitempty"`
}

// Node 增加字段
type Node struct {
    // ... 现有字段 ...
    SysInfo        *SysInfo          `json:"sysinfo,omitempty"`
    ClientStatuses []ClientTunnelStatus `json:"client_statuses,omitempty"`
    RTT            int64             `json:"rtt,omitempty"` // 毫秒
}

// ClientTunnelStatus 客户端上报的隧道状态
type ClientTunnelStatus struct {
    Name          string `json:"name"`
    Type          string `json:"type"`
    Running       bool   `json:"running"`
    Connected     bool   `json:"connected"`
    SerialOpen    bool   `json:"serial_open,omitempty"`
    MQTTConnected bool   `json:"mqtt_connected,omitempty"`
    Clients       int    `json:"clients,omitempty"`
    PID           int    `json:"pid,omitempty"`
    UptimeSeconds int64  `json:"uptime_seconds,omitempty"`
    BytesIn       uint64 `json:"bytes_in,omitempty"`
    BytesOut      uint64 `json:"bytes_out,omitempty"`
    Error         string `json:"error,omitempty"`
}
```

### 4.3 新增 API 路由

```
POST /api/v1/tunnels/{name}/action   # tunnel_action
POST /api/v1/tunnels/{name}/health   # health_check
POST /api/v1/nodes/{id}/restart      # restart
```

## 5. 兼容性策略

- 所有新字段使用 `omitempty`，旧版本客户端/服务端忽略未知字段
- `ping` 增强：`ts == 0` 视为不支持 RTT 测量，双方兼容
- `tunnel_status`：旧客户端不上报 → 服务端 `ClientStatuses` 为空 → 管理后台显示"状态未知"
- `tunnel_action`：旧客户端收到未知命令 → 返回 `{"cmd":"err","msg":"unknown command"}` → 服务端提示"客户端不支持此操作"
- `sysinfo`：旧客户端不上报 → `Node.SysInfo` 为 nil → 前端不显示系统信息区域

## 6. 风险与约束

| 风险 | 缓解措施 |
|------|---------|
| tunnel_status 上报频率过高导致控制流拥堵 | 默认 60s 间隔，仅在状态变化时即时上报；服务端可丢弃过频上报 |
| tunnel_action 误操作导致服务中断 | 仅管理员权限（`tunnels:admin`）；start/stop 有幂等保证 |
| restart 导致业务中断 | 需 `nodes:admin` 权限；默认 delay 5s 给业务收尾时间 |
| health_check 并发过多消耗客户端资源 | 服务端侧做频率限制（单隧道 10s 内仅一次） |
| smux stream 超时（10s）不够健康检查用 | health_check 响应超时设为 30s；客户端探测超时 5s |
