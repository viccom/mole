本次改动的总体方向是正确的，且计划中的主体能力已基本落地：

- 节点断开时增加了隧道资源释放入口

但从“可稳定上线、不会破坏原有语义、运行期行为闭环”的角度看，**当前实现还不能判定为完全验收通过**。

本次审查确认存在以下问题：

- `3` 项高风险问题
- `2` 项中风险问题

其中前三项会直接影响原有节点管理与隧道配置行为：

1. 预配置离线节点会被健康检查误删
2. 停止隧道后，TCP/UDP 运行循环不会退出，可能出现错误自旋和日志刷屏
3. UDP 隧道启动函数是阻塞式的，会卡住节点注册、配置更新或恢复流程

结论：

- **本次改动的核心思路正确**
- **本次改动尚未工程化闭环**
- **建议先完成最小修复，再作为“已完成前后端改进”归档**

## 三、总体评价

### 3.1 本次改动的优点

- 方案保持了当前架构，不是大规模推翻式重构
- `StatsTracker` 通过接口注入到 API 层，方向上是低侵入的
- 节点断开清理被收敛为统一回调，思路比散落清理更清晰
- usage API 与后台页面已经形成基本闭环，可观测性方向正确

### 3.2 当前实现的主要不足

- 生命周期设计只处理了“关闭监听器”，没有处理“运行循环如何退出”
- 健康检查把“离线预配置节点”和“掉线节点”混成了一类
- UDP 启动方式与 TCP 不一致，破坏了原有配置应用路径的时序
- 统计主键设计过于乐观，默认隧道名全局唯一
- 前后端接口升级不完全同步，HTTPS 展示存在遗漏

## 四、详细问题与修复建议

## 4.1 高风险问题一：预配置离线节点会被健康检查误删

### 现象

当前健康检查逻辑会把以下两类节点都加入清理列表：

- `Status == offline`
- `LastHeartbeat` 超时

而系统原本就支持“预配置节点”语义：

- 后台创建节点时，节点状态就是 `offline`
- 这类节点是配置实体，不代表连接异常
- 它们应该长期存在，等待未来某个客户端上线后接管

### 原因

本次改动为了覆盖“心跳超时路径也触发资源回收”，在 `cleanupDeadNodes()` 中扩大了清理范围，但没有区分两种语义完全不同的 `offline`：

- **预配置离线**：业务合法状态
- **连接断开后离线**：运行时清理状态

`nodeMgr.Disconnect()` 的语义又是“直接从运行态删除节点”，因此这不是简单标记，而是删除。

### 影响

- 后台手工创建的离线节点会在下一轮健康检查后从 `nodeMgr` 消失
- 节点列表、节点详情、隧道编辑、归属过滤都可能出现异常
- 这会破坏原有“先创建节点配置，再等待客户端接入”的工作流

### 风险等级

`P0`

### 建议的优雅修复

将健康检查的清理条件收紧为：

- 只清理**在线但心跳超时**的节点

可选增强方案：

- 为 `nodeMgr` 增加 `HasSession(nodeID)` 或同等能力
- 只对“有运行态会话但已失联”的节点触发断开清理

不建议继续使用“`offline` 一概清理”的判定方式。

---

## 4.2 高风险问题二：停止隧道后运行循环不会退出，可能错误自旋

### 现象

本次通过 `ReleaseNodeResources()` 调用了：

- `gateway.StopTunnel(t.Name)`

但 `StopTunnel()` 当前只做一件事：

- 关闭 registry 里记录的 listener / UDP adapter

而 TCP / UDP 的实际运行循环：

- TCP：`Accept()` 循环
- UDP：`ReadFromUDP()` 循环

并没有自己的隧道级取消信号，只监听全局 `ctx.Done()`。

### 原因

本次改动把“关闭底层监听器”当成了“整个隧道资源清理完成”，但实际上一个完整的 runtime 生命周期至少包含：

- 监听器/连接句柄
- 接收循环 goroutine
- 会话清理 goroutine
- 统计与日志行为

当前实现缺少“隧道级 context / cancel / done”这一层，所以循环收到 `use of closed network connection` 之类错误后，只会：

- 记录错误
- `continue`

结果就是 goroutine 不退出。

### 影响

- 关闭后仍有 goroutine 残留
- 日志持续刷 `accept error` / `UDP read error`
- CPU 产生无意义消耗
- 长时间运行后，新的“资源泄漏”会从 fd 泄漏转成 goroutine 与日志风暴

### 风险等级

`P0`

### 建议的优雅修复

为每条隧道引入独立 runtime handle，例如：

- `context.Context`
- `cancel func`
- `done chan struct{}`
- 底层 listener/udp conn

推荐改造方向：

1. `StartTCP()` / `StartUDP()` 创建隧道级 `tunnelCtx`
2. registry 保存的不再只是 `net.Listener`，而是完整 runtime handle
3. `StopTunnel()` 先 `cancel()`，再关闭底层句柄
4. 接收循环在以下情况直接退出而不是 `continue`：
   - `tunnelCtx.Done()`
   - `ctx.Done()`
   - `net.ErrClosed`

这样才能真正实现“资源回收闭环”。

## 4.3 高风险问题三：UDP 启动是阻塞式的，会卡住配置应用链路

### 现象

`applyRuntimeTunnels()` 会同步调用：

- `gateway.StartUDP(ctx, tunnel)`

但当前 `StartUDP()` 不是“启动后立即返回”的模式，而是：

- 绑定 UDP 端口
- 初始化 session map
- 直接进入永久 `ReadFromUDP()` 循环

### 原因

TCP 启动逻辑是“主函数返回，goroutine 执行循环”，UDP 实现却是“主函数本身进入循环”，两者生命周期模式不一致。

这意味着任何调用 `StartUDP()` 的地方，都会把当前业务流程卡在 UDP 读取循环里。

### 影响

以下原有功能都会受到影响：

- 节点注册成功后的持久化配置加载
- `tunnel_update` 后的服务端运行态刷新
- 后台通过 API 修改隧道配置
- 节点重连后恢复持久化隧道

表现可能是：

- 接口迟迟不返回
- 节点注册流程卡住
- 更新配置后前端一直 loading

### 风险等级

`P0`

### 建议的优雅修复

让 UDP 启动与 TCP 完全保持同一模式：

- `StartUDP()` 只负责初始化、监听与注册
- 真实读取循环放入 goroutine
- 函数在“监听已成功建立”后立即返回

这属于非常典型的最小改动修复，不需要改协议，也不需要改上层调用方式。

---

## 4.4 中风险问题四：HTTPS 隧道的后台访问地址展示不正确

### 现象

后端已经把 `https` 纳入：

- usage API 返回
- tunnel stats 汇总

但前端 `tunnelAccessUrl()` 只对 `http` 做域名 URL 构造，没有正确覆盖 `https`。

### 原因

接口模型已经升级，页面展示逻辑没有同步升级。

### 影响

- 隧道列表中 HTTPS 隧道看起来像“没有访问地址”
- 运维会误判为 HTTPS 隧道不可访问或尚未支持

### 风险等级

`P1`

### 建议的优雅修复

把 `http` 与 `https` 的 URL 构造统一处理：

- 类型是 `http` 或 `https` 时，优先使用域名访问方式
- scheme 根据隧道类型决定

这是一个非常小的前端修复。

---

## 4.5 中风险问题五：运行时统计按隧道名单键建模，存在串台风险

### 现象

当前 `StatsTracker` 的 key 是：

- `tunnel.Name`

`Usage` API 和前端 `usageMap` 也都按 `name` 关联。

### 原因

当前实现隐含假设是“隧道名全局唯一”，但代码里真正落实的校验只有：

- 同一节点内不允许重复隧道名

并没有看到全局唯一约束。

### 影响

如果两个不同节点使用相同隧道名，会出现：

- 统计数据混合
- usage API 关联错位
- 前端 `usageMap[item.name]` 被覆盖

这不会立即中断流量转发，但会让监控数据失真，排障结论不可信。

### 风险等级

`P1`

### 建议的优雅修复

把统计 key 升级为复合键，例如：

- `nodeID + "/" + tunnelName`

并统一封装 helper：

- tracker 写入时使用复合键
- usage API 读取时使用复合键
- 前端 map 也改用 `${node_id}:${name}`

这样不需要对外 API 做大改，只是内部关联更准确。

## 五、这次改动对原有功能的影响评估

## 5.1 已确认会影响原有功能的点

### 1. 预配置离线节点管理

原有能力：

- 后台可以先创建离线节点，等待客户端未来上线

当前影响：

- 健康检查会误删这类节点的运行态记录

结论：

- **已影响原有功能**

### 2. UDP 隧道配置更新链路

原有能力：

- 节点注册、配置恢复、后台更新应快速完成

当前影响：

- 一旦进入 `StartUDP()`，调用链可能被阻塞

结论：

- **已影响原有功能**

### 3. 节点断开后的服务端稳定性

原有问题：

- 端口和监听器可能不释放

本次改动后的新情况：

- 端口可能释放了，但 goroutine 和错误循环未退出

结论：

- **旧问题未完全闭环，并引入新的稳定性风险**

## 5.2 当前看起来未明显影响原有功能的点

### 1. HTTP/TCP 主转发链路

- 新增统计埋点本身没有看到直接破坏 HTTP/TCP 转发语义
- 现有测试也没有显示这两条主链路已被明显打断

### 2. 权限过滤主链路

- usage API 仍沿用了原有 tunnels 资源的权限判定方式
- 普通用户只看自己节点的 usage，这一点实现方向正确

### 3. 原有 stats API

- `/api/v1/tunnels/stats` 只是补充了 `https_tunnels`
- 旧字段语义未发生破坏性变化

## 七、结论

本次改动不是“方向错误”，而是“收尾不完整”。

可以这样概括：

- 设计方向：正确
- 主体落地：基本完成
- 生命周期闭环：未完成
- 原有功能兼容：存在实质性影响
- 是否建议直接验收：不建议

建议处理顺序：

1. 先修复 `health.go` 的误删逻辑
2. 再修复 TCP/UDP 隧道级生命周期
3. 让 `StartUDP()` 改为异步启动
4. 再补统计主键和 HTTPS 展示这类中风险问题
5. 最后补齐回归测试
