## 三、🔴 严重问题详述

### SEC-01：Challenge 形同虚设，无防重放、无防嗅探

**文件**
- `internal/tunnel/control.go:328-368`（服务端发 challenge + 读取应答）
- `moleAgent_client/internal/transport/dialer.go:196-235`（客户端读取并丢弃 challenge）

**问题**
服务端在 `control.go:329-339` 生成 32 字节随机 challenge 并写入连接后，`control.go:360-368` 只把应答解析为 `struct{ Token string }`，challenge **未参与任何 HMAC/签名校验**。客户端侧 `dialer.go:198-201` 用 `io.ReadFull` 读出 challenge 后直接丢弃，`dialer.go:205-211` 明文发送 `{"token": "<原始token>"}`。

即所谓 "Challenge-Response 认证" 实际是**明文 token 直传**：challenge 既未绑定会话，也未用于派生密钥，无法防重放、无法防嗅探。

**影响**
- 未启用 TLS（`server.tls.enabled: false`，且默认配置即为 false）时，中间人可嗅探 `mat_` token 并无限期重放，完全接管该用户的节点接入能力。
- KCP 走 AES 加密可缓解；TCP/WS 明文模式下风险成立。

**修复建议**
将应答改为 `HMAC-SHA256(challenge, token)` 或 `sha256(challenge || token)`，服务端用自身持有的 token hash/明文侧复算比对；若不打算实现，应删除该流程以避免"看起来安全"的误导。

### SEC-02：`register` 不校验节点归属，跨租户劫持节点

**文件**
- `internal/tunnel/control.go:718-842`（handleRegister，尤其 `:745-748` 归属赋值、`:838-840` 落库）
- `internal/tunnel/control.go:1010-1030`（`persistNode` 覆盖式落库）

**问题**
`handleRegister` 在 `control.go:745-748` 直接把认证凭据携带的归属写入内存节点：

```go
if grant := state.grant; grant != nil {
    node.OwnerUserID = grant.UserID
    node.AccessTokenID = grant.AccessTokenID
}
```

但 `cmd.NodeID` 的合法性校验（`control.go:719-726`）只校验**格式**（8 字符、首字母、其余字母数字），**未校验该 node_id 在持久层的 OwnerUserID 是否等于 `grant.UserID`**。当 `nodeMgr.Add` 因内存无此节点而成功（`control.go:759`），随后 `persistNode`（`control.go:1010-1030`）走 `Update` 分支把持久层记录整体覆盖，`OwnerUserID` 被改写为攻击者。

**影响**
任何持有有效 `mat_` token 的普通用户，只要构造 `{"cmd":"register","node_id":"<他人预配置的nodeId>"}`，即可把他人（或 system 归属）的预配置/离线节点**连配置带归属一起夺取**，包括该节点下的全部隧道。这是跨租户的越权，破坏 README「节点归属与资源可见性」承诺的隔离模型。

**修复建议**
注册时先 `nodeRepo.GetByID(cmd.NodeID)`，若存在持久化记录且 `persisted.OwnerUserID != "" && persisted.OwnerUserID != grant.UserID` 且 `grant.UserID != system`，则拒绝注册（回 `err` 并关闭），仅允许同归属重连。

### SEC-03：明文 Token 落库并经 API 回显

**文件**
- `internal/tunnel/control.go:735`（`Token: cmd.Token`）
- `internal/api/node_handler.go:148`（`Token: req.Token`）、`:127`（`Get` 返回整个 `*core.Node`）
- `internal/storage/node_repo.go:22-29`（整 Node JSON 序列化落 SQLite）

**问题**
`core.Node.Token` 字段被完整写入持久层并在 API 响应中回显。而控制端口的真实认证走的是 `authenticator.AuthenticateNodeToken`（基于 access_token 的 sha256 hash），`Node.Token` **不参与任何认证判定**，属纯冗余的明文凭证泄漏面。

**影响**
- 任何持有 `nodes:read` 的用户（含 `operator` 角色）可通过 `GET /api/v1/nodes` / `GET /api/v1/nodes/{id}` 读取他人节点的明文 token。
- 数据库文件或备份泄漏时，明文 token 直接暴露。

**修复建议**
删除 `core.Node.Token` 字段；或在 `node_repo` 落库前与 `node_handler` 响应前统一置空/脱敏（保留 `TokenPrefix` 语义）。

### SEC-04：`refresh` 固化旧角色，撤权不生效

**文件**
- `internal/auth/service.go:96-112`（`RefreshToken`）
- `internal/api/resource_scope.go:10-25`（`IsAdmin` 依据 JWT 内嵌 roles）

**问题**
`RefreshToken` 已在 `service.go:103-109` 回库复查**用户状态**（禁用/删除会被拒），但 `service.go:110` 直接 `s.jwtMgr.GenerateToken(claims)` —— 复用**旧 token 的 claims 快照**，其中 `Roles` 是签发时的值，**从不回库重查角色**。

而 `resource_scope.go:19-23` 的 `IsAdmin` 依据 `claims.Roles` 判定，`CanAccessNode`/`FilterNodes`/`checkNodeOwnership` 及 WebSSH 归属层（`webssh_handler.go:88` 附近）全部依赖它。

**影响**
管理员对某用户撤销 `admin` 角色后，只要该用户持续调用 `POST /api/v1/auth/refresh`（token 未过期即可反复续期），JWT 内 `roles:["admin"]` 永不更新 → 对全部节点/隧道/WebSSH 永久保持管理员视图与操作权限。等同于**撤权不生效**。反之，新授予的角色也无法通过 refresh 获得（需重新登录），行为不对称。

**修复建议**
`RefreshToken` 中调用 `rbac` / `userRepo` 重新查询该用户当前角色列表与权限，用最新值构造 claims 后再签发。

- `internal/config/config.go:331-342`（`AdminUser()` 默认 `admin`/`admin`）
- `internal/storage/db.go:128`（种子管理员落库）
- `cmd/moleagent-serv/main.go:154-163`（节点控制端口默认 token）

**问题**
- `config.go:335-340`：未设 `MA_ADMIN_USER`/`MA_ADMIN_PASS` 时，种子管理员为 `admin`/`admin`。
- `main.go:154-163`：未设 `-nodetoken`/`MA_NODE_TOKEN` 时，回退为公开仓库可查的 `"default-node-token-change-me"`（代码中 `main.go:160-162` 已自带 WARN，但**仅告警不拒绝启动**）。

### SEC-06：AccessKey 绕过范围 = 全量 admin，含 RCE 面

**文件**
- `internal/auth/middleware.go:55-66`（RBAC 旁路）、`:74-80`（AccessKey 身份构造）
- `internal/api/resource_scope.go:16-18`（归属层视为 admin）
- `cmd/moleagent-serv/main.go:539`（`POST /api/v1/self-update`，权限 `system:admin`）

**问题**
`middleware.go:56` 判断 `claims.UserID != "access_key"` 时**跳过全部 RBAC 校验**；`resource_scope.go:16-18` 同步把该身份视为 admin，故归属过滤也全部放行。AccessKey 无 scope、无过期、无审计区分（与真实用户身份共用同一路径）。

**影响**
单一静态共享密钥（经 `W-Access-Key` 头传递，`middleware.go:76-79`）一旦泄漏，攻击者可：
- 调用 `main.go:539` 的 `POST /api/v1/self-update`，从外部 URL 下载二进制并重启（`internal/api/update_handler.go`）→ **远程代码执行 / 供应链接管**；
- 删除用户、重置任意密码、读写 `/api/v1/config`、管理 AccessKey 自身。

**修复建议**
至少将 `self-update`、`accesskey` 管理、用户删除排除在旁路之外；更彻底的做法是给 AccessKey 引入 scope 白名单并记录审计日志。

### SEC-07：登录端点默认无暴力破解防护

**文件**
- `configs/config.example.yaml:66-68`（`ratelimit.api.enabled: false`）
- `cmd/moleagent-serv/main.go:457`（`router.RegisterPublic("POST", "/api/v1/auth/login", authH.Login)`）

**问题**
默认配置中 API 限流总开关为 `false`（`config.example.yaml:68`），而 `/api/v1/auth/login` 是公开端点（`main.go:457`）。在 bcrypt cost=12 下每次尝试约数百毫秒，攻击者可低成本进行不限速的密码撞库，同时以大量登录请求消耗服务端 CPU。

注：MQTT 侧有按用户名节流（`internal/mqtt/broker.go:176-182` 附近），HTTP 登录侧无对应机制，两端防护不对称。

**修复建议**
为登录端点配置**独立**的限速/失败锁定（不随 `ratelimit.api.enabled` 总开关关闭），可按 IP + 用户名双维度计数。

## 四、🟡 中等问题详述

### SEC-08：`users:write` 可重置任意用户（含 admin）密码

**文件**：`internal/api/user_handler.go:143-157`（子路径分发）、`:368-391`（`resetPassword`）、`cmd/moleagent-serv/main.go:492`

**问题**：`main.go:492` 以 `("users","write")` 注册 `PUT /api/v1/users/`，而 `user_handler.go:153-157` 将 `.../password` 子路径分发给 `resetPassword`，该 handler **不校验旧密码**。故仅持有 `users:write` 的非管理员角色即可执行 `PUT /api/v1/users/admin/password` 接管管理员账户。

**影响**：水平→垂直提权。任何被授予 `users:write` 的自定义角色（README 示例中的角色可自由组合权限）均可夺取 admin。

**修复建议**：`resetPassword` 针对他人账户（尤其 admin 角色持有者）要求 `users:admin` 权限；或禁止重置比自己权限更高的账户。

**关联**：见 DOC-01 —— README 声称该接口需 `users:admin`，与实际代码 `users:write` 不符。

---

### SEC-09：MQTT Publish API 绕过 topic ACL

**文件**：`internal/api/mqtt_handler.go:43-67`、`internal/mqtt/broker.go:102-104`

**问题**：API 发布走 broker 的 inline client，**不经过 `aclHook`**。仅有 `mqtt:write` 的普通用户可向任意 topic（含他人 `/mole/<nodeId>/...`）发布消息，绕过节点归属隔离。

**修复建议**：Publish 前对非 admin 身份执行与 `aclHook` 一致的 topic 归属校验。

---

### SEC-10：Cookie / query token 认证无 HttpOnly、无 CSRF 防护

**文件**：`internal/auth/middleware.go:92-98`（Cookie 读取）、`:100-106`（`?token=` query 读取）

**问题**：全仓库无服务端 `Set-Cookie`，Cookie 由前端 JS 写入 → **非 HttpOnly**，任一 XSS 即可窃取 token；所有状态变更端点均接受该 Cookie 且无 CSRF token 校验。此外 `?token=` 查询参数认证会把 JWT 写入浏览器历史、Referer 与反向代理访问日志。

**修复建议**：由服务端下发 `HttpOnly; Secure; SameSite=Lax` Cookie；为状态变更端点增加 CSRF 校验；评估移除 query token 认证（或严格限定到 WebSocket 升级路径并短时效化）。

---

### SEC-11：MQTT 无 TLS，凭据明文传输

**文件**：`cmd/moleagent-serv/main.go:271-272`

**问题**：内置 broker 的 TCP/WS 监听未启用 TLS，客户端口令（bcrypt 哈希前的明文）直接过网。启动日志中已有 WARN 提示。

**修复建议**：支持配置 MQTT TLS 证书；或在文档中明确要求部署在受信网络 / 前置 TLS 终结代理。

### SEC-12：隧道凭据明文落库的默认路径

**文件**：`cmd/moleagent-serv/main.go:81-84`

**问题**：未配置 `tunnel_secret` 且 `jwt_secret` 为自动生成时，WebSSH 口令/私钥等 Para 内容以明文落库。默认配置 `jwt_secret: ""`（见 `configs/config.example.yaml`）恰好命中该路径。

**修复建议**：强制要求 `tunnel_secret`（或从显式配置的 `jwt_secret` 稳定派生），缺失时拒绝启动而非降级为明文。

### SEC-13：控制端口认证无失败限速

**文件**：`internal/tunnel/control.go:311-402`

**问题**：控制端口认证失败仅记日志并关闭连接，无 per-IP 限流（`ratelimit` 包只覆盖 API 与网关）。配合 SEC-05 的公开默认 token，控制端口在默认部署下等同于开放注册；若运维改用弱口令旧全局 token，则可被在线爆破。

**修复建议**：为控制端口认证接入 per-IP 失败计数与封禁（可复用 `internal/ratelimit`）。

### SEC-14：自助改密无强度校验

**文件**：`internal/auth/service.go:115-128`

**问题**：`ChangePassword` 校验了旧密码（`service.go:120-122`），但**未校验新密码长度/复杂度**。而 `Create`/`Update`/`resetPassword` 路径均有 ≥8 位校验，仅自助改密遗漏。

**修复建议**：在 `ChangePassword` 内复用统一的口令强度校验函数。

### REL-01：`listen_port` 完全无校验，`ErrPortInUse` 定义后从未使用

**文件**：`internal/service/tunnel_service.go:75-115`（`validateTunnel` 只校验 `target`）、`internal/tunnel/tcp.go:14-17`、`internal/core/errors.go:33`

**问题**
- 租户可提交 `listen_port: 22` / `9983` 等敏感或服务自身端口，无范围与冲突校验。
- 同端口配置两条隧道时，第二条 `net.Listen` 失败，但 `applyRuntimeTunnels`（`tunnel_service.go:730-736`）只 `slog.Error` 后**继续**，API 仍返回成功；更严重的是此前旧监听器已被 `StopTunnel` 停掉 → 该隧道**静默全断**而管理端显示正常。

**修复建议**：校验端口范围（1-65535）、隧道间唯一性、与服务自身端口（9980/9981/9983/1883/1882）冲突；监听失败时回传 `ErrPortInUse` 并回滚为旧监听器。

---

### REL-02：`register` 携带的隧道列表不经校验即入内存

**文件**：`internal/tunnel/control.go:737`

**问题**：`control.go:737` 将 `cmd.Tunnels` 直接赋值给 `core.Node.Tunnels` 并触发 `RebuildIndex`。仅当持久层为空才走 `SyncFromClient`（`control.go:818-821`），且其校验失败只 `Warn` 不回滚；隧道条数无上限。

**影响**：客户端上报的畸形/海量隧道会滞留内存并参与路由索引，构成内存与路由污染面（恶意客户端可借此放大服务端内存）。

**修复建议**：注册时先跑 `validateTunnels` + 条数上限（如 ≤ 256），失败则拒绝注册。

---

### REL-03：UDP 同源地址并发建会话竞态 → 流/配额泄漏

**文件**：`internal/tunnel/udp.go:121-229`（尤其 `:225` 回插 `sessions[key]`）

**问题**：首个数据包解锁后创建会话，回插 `sessions[key]` 时**未检查是否已有并发会话**。并发场景下后写覆盖先写，被覆盖会话的 smux stream、读协程与 `AcquireConn` 配额需等对端流死亡才回收；若该流长期空闲则泄漏至隧道停止。

**修复建议**：回插时做 CAS/存在性检测，冲突则关闭败者并释放配额；或为每个 key 使用 once 语义的会话创建。

---

### REL-04：UDP 完全绕过 `max_concurrent` 信号量

**文件**：`internal/tunnel/udp.go`（全文无 `tg.sem.Acquire`）
**对照**：`internal/tunnel/tcp.go:60-63`、`internal/tunnel/http.go:136-140`

**问题**：TCP/HTTP/WS 均受 `tg.sem` 信号量约束，UDP 会话数仅受 60s 过期限制，`max_concurrent`（默认 50000）对 UDP 形同虚设。

**修复建议**：UDP 建会话路径接入同一信号量，或为 UDP 单独设会话数上限。

---

### REL-05：网关 `http.Server` 无任何超时

**文件**：`cmd/moleagent-serv/main.go:368-371`（`gatewaySrv`）、`internal/tunnel/http.go:119-121`（`RegisterHTTP` 内的 srv）
**对照**：`cmd/moleagent-serv/main.go:354-359`（`apiSrv` 已设 `ReadHeaderTimeout: 10s`）

**问题**：`gatewaySrv` 仅设 `Addr` 与 `Handler`，无 `ReadHeaderTimeout`/`ReadTimeout`/`IdleTimeout`，可被 slowloris 类慢速请求占满连接池。

**修复建议**：对齐 `apiSrv`，至少设置 `ReadHeaderTimeout` 与 `IdleTimeout`。注意 WebSocket 长连接场景需避免设置过短的 `ReadTimeout`。

---

### REL-06：`probeOldSession` 用真实 `tunnel_push` 当探针（有副作用）

**文件**：`internal/tunnel/control.go:844-875`

**问题**：探测旧会话是否存活时，真的下发一次 `tunnel_push` 配置推送作为探针；3 秒未收到响应即判定旧会话死亡并执行置换（`control.go:763-781`）。

**影响**：慢客户端（高延迟链路、客户端繁忙）会被**误判为假死**而被置换，产生非预期的会话抖动；同时探针本身对旧客户端产生了一次真实配置变更副作用。

**修复建议**：新增无副作用的专用 `probe` 命令（仅回 `pong`/`ok`），并放宽判死阈值或改为多次探测。

---

### REL-07：删除用户级联非原子且吞错

**文件**：`internal/storage/user_repo.go:131-143`、`internal/api/user_handler.go:220-308`

**问题**：`user_repo.go:131-143` 对 passwords / user_roles / usernames 的删除不检查错误。若 `user_roles` 删除失败，而同名用户随后被重建（`Create` 不清 `user_roles`），新用户将**继承已删除用户的角色**。`user_handler.go:220-308` 的级联（AccessToken 禁用、节点归属改 system）同样无事务，中途失败留残留。

**修复建议**：Redka 基于 KV 无事务，需改为"先删关联后删主体"的严格顺序 + 每步错误上抛；或引入补偿日志/幂等重试。

### REL-08：HTTP 代理未剔除 hop-by-hop 头；HTTPS 类型域名路由不一致

**文件**：`internal/tunnel/http.go:294-297`、`internal/tunnel/registry.go:243-245`、`internal/tunnel/http.go:97-98,189`

**问题**
- `http.go:294-297` 原样拷贝上游响应头，未剔除 `Connection`、`Transfer-Encoding`、`Keep-Alive` 等 hop-by-hop 头 → 可能造成响应分帧歧义。
- 域名索引（`registry.go:243-245`）与兜底扫描（`http.go:189`）只收录 `TunnelTypeHTTP`，而 `findNodeTunnel`（`http.go:97-98`）接受 HTTPS → 配置了 `domain` 的 HTTPS 类型隧道**永远无法按域名路由**，行为不一致。

**修复建议**：按 RFC 7230 剔除 hop-by-hop 头；统一域名路由的类型判定集合（或将 HTTPS 类型明确限定为 SNI 透传路径）。

### PERF-01：`biCopy` 每连接现分配 2×1MB 缓冲

**文件**：`internal/tunnel/util.go:16`（`const biCopyBufferSize = 1024 * 1024`）、`:22-24`

**问题**：每个双向转发连接现分配两个 1MB 缓冲。默认 `max_concurrent = 50000` 时，理论峰值可达 100GB 级内存申请（实际受连接数限制，但压力可观）。

**修复建议**：改用 `sync.Pool` 复用缓冲，或将缓冲尺寸下调（如 32-64KB）后按需扩容。

## 八、整体评价

### 优点

1. **架构设计良好**：`internal/core` 为纯领域模型 + 接口（`NodeRepo`/`TunnelConfigManager`/`NodeAccessAuthenticator`），`tunnel` 包不反向依赖 `service`；节点管理器 256 分片；监听器/运行时/统计/限速职责分离清晰；配置变更收敛到 `TunnelConfigService` 单一入口，`pairingMu` 封闭 TOCTOU 的做法成熟。
2. **防御意识强**：代码中保留了多轮审查迭代痕迹（`审查 #N` / `复审 RN` 注释），对资源泄漏、竞态、OOM 等历史坑有针对性修复（`readBoundedLine`、`biCopy` 半关、UDP 幂等销毁、代际防误扣）。
3. **凭据处理基本合格**：JWT 固定 HS256 并校验 HMAC 族（防 `alg=none`/算法混淆）；密码 bcrypt；access token 只存 sha256；AccessKey 使用常量时间比较；`/config` 已脱敏。
4. **归属过滤覆盖较全**：节点/隧道的 Get/Update/Delete/connection 各分支均接入了归属校验。

### 主要短板

1. **安全边界是薄弱面**：内部逻辑扎实，但外围暴露面（认证协议空转、租户隔离缺失、凭证卫生、默认值）问题集中。
2. **贯穿性缺陷主线——"权限真相源不统一"**：RBAC 中间件查库（`middleware.go:57`）、归属层查 JWT 快照（`resource_scope.go:19`）、`refresh` 又不刷新快照（`service.go:110`），三者错位直接造成 SEC-04 的撤权滞留。
3. **默认值不安全**：SEC-05 / SEC-07 / SEC-12 均属"开箱即不安全"。
4. **存储层一致性脆弱**：Redka 基于 KV 无事务，多步写依赖手工补偿（SEC-08 关联、REL-07、QUA-01）。

### 测试覆盖

- **服务端**：284 个测试函数 / 43 个测试文件，覆盖 auth（jwt/rbac/password）、storage、ratelimit、mqtt broker 与多数 handler，质量不错。
- **缺口**：`auth_handler`（登录/refresh 无测试——SEC-04 正源于此）、`system_handler`、`webssh_handler`、`feishu`/`dingtalk_handler`、`update_handler` 均无测试；核心竞态路径（同 node_id 重连置换的 `Add`→`AddSession` 窗口、断连清理与注册并发、UDP 建会话竞态）缺少时序级测试。
- **建议优先补测**：refresh 角色刷新（SEC-04）、AccessKey 旁路范围（SEC-06）、注册归属校验（SEC-02）。

### 修复优先级建议

| 优先级 | 项目 | 理由 |
|--------|------|------|
| P0 | SEC-02、SEC-04 | 改动小、收益大：前者阻断跨租户越权，后者修复撤权失效 |
| P0 | SEC-03、SEC-06 | 凭证泄漏面与 RCE 面，需尽快收敛 |
| P1 | SEC-05、SEC-07 | 默认值安全化，一次改动消除"开箱即不安全" |
| P1 | SEC-01、SEC-08 | 认证协议与提权路径 |
| P2 | REL-01、REL-04、REL-05 | 稳定性与资源保护 |
| P3 | 其余 🟡 / 🟢 | 按迭代节奏排期 |
