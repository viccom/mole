# WebSSH 文件传输实施方案

**日期**：2026-06-10
**分支**：`feature/webssh`
**目标**：在现有 WebSSH 终端功能基础上，增加 SFTP 文件管理（列表/上传/下载/删除/建目录），复用现有 WebSocket 连接和 smux 隧道。

## 一、开源项目深度对比结论

### 1.1 go-eoocc-webssh（Vue2 + Gin）

| 维度 | 详情 |
|------|------|
| 架构 | 直连模式：Gin 服务端直接 SSH 到目标，前端 REST/WS 直接交互 |
| SFTP | `core/sftpclient.go` 仅 65 行，封装了 `Upload`/`Download`/`Mkdirs` |
| 前端 | Vue2 + Element UI，`FileList.vue` 组件 230 行，拖拽上传 + WebSocket 进度轮询 |
| 连接管理 | **无复用**——每次文件操作都调用 `CreateSftp()` → `GenerateClient()` 新建 SSH 连接 |
| 进度上报 | 全局变量 `WcList []*WriteCounter`，另一个 WebSocket 轮询，**并发不安全** |
| 安全性 | SSH 凭证 base64 编码后作为 URL 参数传递，密码明文出现在 GET 请求中 |

**可借鉴点**：
- 前端 `FileList.vue` 的交互流程：路径导航、目录进入/返回、行点击区分文件/目录
- `detectHomeDir` 逻辑：依次尝试 `getwd()` → `/usr/home/$USER` → `/home/$USER` → `/home`

**不可借鉴点**：
- 每次新建 SSH 连接的模式（我们有连接池）
- 全局变量进度追踪（并发不安全）
- base64 凭证传参（安全风险）

### 1.2 go-webssh（Vue3 + Gin）

| 维度 | 详情 |
|------|------|
| 架构 | 会话管理模式：`CreateSessionId` 建连接 → `sync.Map` 存会话 → REST/WebSocket 复用 |
| SFTP | `ssh_sftp.go` 283 行，`connect()` 同时创建 `sshClient` + `sftpClient`，完整 CRUD |
| 前端 | Vue3 SPA 编译后嵌入，路由: `/api/sftp/*` (list/download/upload/delete/create_dir) |
| 连接管理 | `SshConn` 结构体同时持有 `sshClient`、`sftpClient`、`sshSession`，生命周期统一管理 |
| 会话清理 | `cleanNoActiveSession` 定时扫描 `LastActiveTime`，超时自动 `DeleteOnlineClient` |
| 文件操作 | 列表(`ReadDir`)、下载(`sftp.Open → WriteTo`)、上传(`multipart → sftp.Create`)、删除(`RemoveAll`)、建目录(`MkdirAll`) |

**可借鉴点**：
- **SSH 连接复用**：`ssh.Client` 上同时创建 `sftp.Client`，终端和文件共享同一连接
- **会话生命周期**：`DeleteOnlineClient` 统一关闭 `ws/sshSession/sftpClient/sshClient`
- **文件操作完整度**：列表/上传/下载/删除/建目录 五项功能齐全
- **上传进度**：用 gin 原生的 `on-progress` 事件，无需额外 WebSocket
- **列表响应格式**：`{files, file_count, dir_count, paths, current_dir}` 含面包屑路径

**不可借鉴点**：
- REST API 直连 SFTP（我们是穿透架构，服务端无法直接 SSH）
- `session_id` 存在 URL 参数中（我们用 JWT 认证）
- 完整运维平台代码量（50+ Go 文件），需要大幅精简

### 1.3 最终借鉴策略

以 **go-webssh** 为主参考，提取其 SFTP 操作封装和会话管理模式，但传输通道从 REST 改为 WebSocket binary 消息（适配穿透架构）。

## 二、架构约束分析

### 2.1 moleAgent 穿透架构

```
浏览器 (xterm.js + FilePanel)
  ↕ WebSocket binary (复用现有连接)
服务端 (webssh_handler.go)
  ↕ smux stream (复用现有流)
客户端 (handler.go)
  ↕ ssh.Client (复用现有连接池)
    ↕ sftp.Client (新增，从 ssh.Client 创建)
SSH 目标服务器
```

**核心约束**：
1. 服务端不直接访问 SSH 目标，只做 WebSocket ↔ smux 透明桥接
2. 文件操作消息必须复用现有 WebSocket 连接（同 tunnel、同认证）
3. 协议格式必须兼容现有 `[type 1B][len 2B BE][payload]` 编码
4. smux 流承载终端数据和文件数据，必须用消息类型区分

### 2.2 现有协议字节空间

| 字节值 | 用途 | 定义位置 |
|--------|------|----------|
| `0x00` | TCP/UDP 流标识头 | `client.go` dispatchStream |
| `0x01` | WebSSH 流标识头 / 终端数据 | `webssh_handler.go` + `handler.go` |
| `0x02` | 窗口大小调整 | 同上 |
| `0x03` | 心跳 | 同上 |
| `0x04-0x0F` | **空闲** | 可分配给文件操作 |
| `0x10+` | 未来扩展 | 保留 |

### 2.3 现有依赖

- **客户端**：Go 1.25.3，已有 `golang.org/x/crypto/ssh`，**无** `github.com/pkg/sftp`
- **服务端**：Go 1.25，已有 `github.com/gorilla/websocket`，**无** `github.com/pkg/sftp`
- `github.com/pkg/sftp v1.13.7` 是 Go SSH 生态标准 SFTP 库，MIT 协议，与 `golang.org/x/crypto/ssh` 配合使用

### 2.4 前端约束

- React 18 + TypeScript + Tailwind CSS（非 Vue）
- 路由：`/admin/webssh/:tunnelName` 全屏页面
- 构建产物 `admin/dist/` 通过 `go:embed` 嵌入服务端
- 所有页面都是函数组件 + Hooks 模式

## 三、协议设计

### 3.1 新增消息类型

在 `0x04-0x0E` 区间分配，与现有 `0x01-0x03` 不冲突：

```
// 终端操作 (0x01-0x03，已有)
0x01  Data       终端输入数据
0x02  Resize     窗口大小调整
0x03  Keep       心跳

// 文件操作请求 (0x04-0x09，浏览器 → 服务端 → 客户端)
0x04  FileListReq     目录列表请求
0x05  FileUploadReq   上传开始请求
0x06  FileUploadData  上传数据块
0x07  FileUploadEnd   上传结束标记
0x08  FileDownloadReq 下载请求
0x09  FileDeleteReq   删除请求
0x0A  FileMkdirReq    创建目录请求

// 文件操作响应 (0x0C-0x0E，客户端 → 服务端 → 浏览器)
0x0C  FileListResp    目录列表响应
0x0D  FileDataResp    文件数据块（下载）
0x0E  FileAckResp     操作确认/错误响应
```

### 3.2 消息帧格式

沿用现有 `writeWebSSHMsg` 的 `[type 1B][len 2B BE][payload]` 编码：

```
[type 1字节][length 2字节 大端][payload]
```

- payload 最大 65535 字节（2 字节长度限制）
- 大文件通过分块传输，每块 ≤ 32KB（WebSocket 读取上限匹配）

### 3.3 各操作 payload 格式

**FileListReq (0x04)**
```json
{"path": "/home/user"}
```

**FileListResp (0x0C)**
```json
{
  "path": "/home/user",
  "home": "/home/user",
  "files": [
    {"name": "doc.txt", "size": 1024, "mode": "-rw-r--r--", "mod_time": "2026-06-10 12:00:00", "is_dir": false},
    {"name": "project", "size": 4096, "mode": "drwxr-xr-x", "mod_time": "2026-06-09 10:00:00", "is_dir": true}
  ]
}
```

**FileUploadReq (0x05)**
```json
{"path": "/home/user/doc.txt", "size": 1048576}
```
后续紧跟多个 `FileUploadData (0x06)` 消息，payload 为原始二进制数据块。

**FileUploadData (0x06)**
```
payload = 原始二进制数据（32KB 分块）
```

**FileUploadEnd (0x07)**
```json
{"path": "/home/user/doc.txt"}
```

**FileDownloadReq (0x08)**
```json
{"path": "/home/user/doc.txt"}
```

**FileDataResp (0x0D)**
```
payload = 原始二进制数据（32KB 分块）
最后一个块后发 FileAckResp(0x0E) 表示完成
```

**FileDeleteReq (0x09)**
```json
{"path": "/home/user/unwanted.txt"}
```

**FileMkdirReq (0x0A)**
```json
{"path": "/home/user/newdir"}
```

**FileAckResp (0x0E)**
```json
{"ok": true, "msg": "", "size": 1048576}
// 或错误响应
{"ok": false, "msg": "permission denied", "size": 0}
```

### 3.4 唯一性约束

当前协议中消息是**请求-响应**模式，每个 WebSocket 连接同时只有一个 WebSSH 终端会话。文件操作与终端共享同一连接，但通过消息类型完全隔离——终端数据走 `0x01`，文件数据走 `0x04-0x0E`，互不干扰。

不需要 request ID，因为：
- 每次只处理一个文件操作（前端在操作进行时禁用其他文件按钮）
- 响应类型与请求类型一一对应
- 如果未来需要并发文件操作，可在 payload 中加 `req_id` 字段

### 4.2 服务端（moleAgent_Serv）— 极小改动

#### 4.2.1 `internal/api/webssh_handler.go` — 透传扩展

服务端是 WebSocket ↔ smux 的透明桥接。现有 `wsToSmux` 已经将所有 WebSocket binary 消息按 `[type][payload]` 转发。**只需移除 `ws.SetReadLimit(32KB)` 对文件消息的限制检查**，因为文件数据块会接近 32KB。

**实际改动**：几乎为零。`wsToSmux` 的 `switch` 只处理 `0x01/0x02/0x03`，其他类型消息直接走 `default`（当前被丢弃）。需要改为：
```go
default:
    // 文件操作消息 (0x04-0x0A) 透传到 smux
    if msgFlag >= 0x04 && msgFlag <= 0x0A {
        if err := writeWebSSHMsg(stream, msgFlag, payload); err != nil {
            return
        }
    }
```

`smuxToWs` 同理：当前只转发原始字节作为终端输出。需要识别文件响应消息（`0x0C-0x0E`）并正确转发。**但这里有个关键问题**：当前 `smuxToWs` 不解析消息类型，直接把 smux 读到的原始字节转发给 WebSocket。

这意味着需要改造 `smuxToWs`，使其也能解析 `[type][len][payload]` 格式的消息。但这样会与终端输出数据冲突——终端输出是**没有**消息类型前缀的裸字节。

**解决方案**：保持 `smuxToWs` 不变（终端输出仍是裸字节）。客户端发送文件响应时，使用一个**新的 smux 流**专门用于文件操作，与终端输出流分离。

### 4.3 传输通道的重新评估

**问题**：当前 WebSSH 的 smux 流中，客户端→服务端方向是结构化消息（`[type][len][payload]`），但服务端→客户端方向（`smuxToWs`）是**裸字节流**（SSH stdout/stderr 直接写入 smux，服务端直接转发）。

如果文件下载响应也走这个裸字节流，终端输出和文件数据会混在一起，无法区分。

**三种解法**：

| 方案 | 思路 | 代价 |
|------|------|------|
| A. 双流 | 终端用一个 smux stream，文件操作用另一个 smux stream | 服务端需开新 stream，改架构 |
| B. 全协议化 | 客户端→服务端也改为结构化消息，所有数据都带 `[type][len][payload]` 头 | 改动大，终端输出需改写 |
| C. 混合流 + 类型头 | 文件响应走结构化消息头，终端输出保持裸字节，用 type 范围区分 | 最小改动，但需 smuxToWs 能解析 |

**推荐方案 C**——改造 `smuxToWs` 使其能够解析混合流：

```
smux → smuxToWs 读取数据:
  解析前 1 字节:
    如果是 0x0C-0x0E → 按 [type][len 2B][payload] 解析，封装为 WS binary 发送
    其他 → 裸字节，作为终端数据直接 WS 发送（兼容现有行为）
```

这在实际中是安全的，因为：
- SSH 终端输出的第一个字节是终端转义序列（`0x1B`）或可打印字符（`0x20-0x7E` 或 UTF-8 多字节 `0x80+`）
- 文件响应类型是 `0x0C-0x0E`，与终端输出首字节不重叠
- 客户端在写入 smux 时，终端输出和文件响应是串行的（同一个 goroutine 的 `byteCounter.Write`），不会交叉

**但有个边界问题**：如果 SSH 输出恰好以 `0x0C`/`0x0D`/`0x0E` 开头（虽然概率极低），会被误判为文件响应。

**更可靠的方案 C'**：客户端在写回 smux 时，终端输出和文件响应都走结构化消息：

```go
// 客户端 byteCounter.Write 改造
func (bc *byteCounter) Write(p []byte) (int, error) {
    // 终端输出也封装为 [type][len][payload] 格式
    n, err := writeWebSSHMsg(bc.w, msgData, p)  // 复用 0x01 类型
    // ...
}
```

这样 smux 流完全结构化，服务端 `smuxToWs` 改为解析所有消息并转发：

```go
func (h *WebSSHHandler) smuxToWs(ws *websocket.Conn, stream io.Reader, tunnelName string) {
    for {
        // 读取 [type 1B][len 2B][payload]
        msgType, payload, err := readWebSSHMsg(stream)
        if err != nil { return }
        // 所有消息都作为 WS binary 转发，前端按 type 区分
        ws.WriteMessage(websocket.BinaryMessage, buildWSMsg(msgType, payload))
    }
}
```

**代价评估**：
- 客户端 `byteCounter` 改为用 `writeWebSSHMsg` 封装——约 10 行改动
- 服务端 `smuxToWs` 改为解析消息——约 30 行改动
- 服务端前端 WS 消息处理增加文件响应分发——约 20 行改动
- **服务端 `wsToSmux` 不改**（现有逻辑已正确）

**方案 C' 的优势**：
1. 流完全结构化，不存在裸字节与结构化消息混合的歧义
2. 所有方向的消息都有明确的类型，未来扩展任何新功能都容易
3. 改动集中且可控

### 5.2 前端消息处理

当前 `ws.onmessage` 只处理终端数据：

```typescript
ws.onmessage = (ev) => {
    if (ev.data instanceof ArrayBuffer) {
        const decoder = new TextDecoder('utf-8')
        term.write(decoder.decode(ev.data))  // 全部当终端输出
    }
}
```

改造为按消息类型分发：

```typescript
ws.onmessage = (ev) => {
    if (ev.data instanceof ArrayBuffer) {
        const buf = new Uint8Array(ev.data)
        if (buf.length === 0) return
        const msgType = buf[0]
        const payload = buf.slice(1)

        switch (msgType) {
            case 0x01:  // 终端数据
                term.write(new TextDecoder().decode(payload))
                break
            case 0x0C:  // 文件列表响应
                handleFileListResp(payload)
                break
            case 0x0D:  // 文件下载数据
                handleFileDataResp(payload)
                break
            case 0x0E:  // 操作确认
                handleFileAckResp(payload)
                break
        }
    }
}
```

**注意**：这要求服务端 `smuxToWs` 转发时也按 `[type][payload]` 格式封装 WebSocket 消息。目前服务端直接转发 smux 裸字节，需要配合方案 C' 改造。

### 5.3 上传实现

参考 go-webssh 和 go-eoocc-webssh 的上传流程，但改为 WebSocket binary 消息：

```typescript
async function uploadFile(file: File, remotePath: string) {
    // 1. 发送上传开始请求
    const req = new TextEncoder().encode(JSON.stringify({
        path: remotePath + '/' + file.name,
        size: file.size,
    }))
    ws.send(buildMsg(0x05, req))

    // 2. 分块读取并发送
    const CHUNK = 32768
    let offset = 0
    while (offset < file.size) {
        const chunk = file.slice(offset, offset + CHUNK)
        const buf = await chunk.arrayBuffer()
        ws.send(buildMsg(0x06, new Uint8Array(buf)))
        offset += buf.byteLength
        onProgress?.(offset, file.size)
    }

    // 3. 发送结束标记
    const end = new TextEncoder().encode(JSON.stringify({ path: remotePath + '/' + file.name }))
    ws.send(buildMsg(0x07, end))
}
```

## 七、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| Phase 1 协议改造导致终端功能回归 | 高 | Phase 1 完成后立即回归测试终端 |
| SFTP subsystem 在目标 SSH 服务器上被禁用 | 中 | `getSFTPClient()` 返回错误时，前端禁用文件管理按钮并提示 |
| 大文件传输占用 WebSocket 带宽影响终端响应 | 中 | 文件数据块发送时加 10ms 间隔让出控制权；或用 `requestAnimationFrame` 节流 |
| `writeWebSSHMsg` 的 2B 长度限制 (64KB) 对大 payload 不够 | 低 | 文件数据块控制在 32KB，远小于 64KB 上限 |
| smux 流窗口满导致文件数据阻塞终端输出 | 中 | 文件传输和终端输出共享同一 smux stream 的窗口，大文件可能填满发送窗口。缓解：文件数据块发送间隔 + 流控 |
| 客户端 `sftpClient` 生命周期与 `sshClient` 不一致 | 中 | `sftpClient` 在 `sshClient` 失效时一并清除，下次文件操作重新创建 |
