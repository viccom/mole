# moleAgent_Serv 最小改动修复实施方案

**文档日期**：2026-04-16  
**对应审查报告**：`2026-04-16-隧道运行时统计与资源回收审查报告.md`  
**目标**：在尽量不改架构、不改外部接口语义、不引入大范围重构的前提下，修复本次“资源回收 + usage 监控”改动中已确认的问题。

---

## 一、方案原则

本次修复严格遵循以下原则：

- 保持现有包结构不变
- 尽量不修改 API 对外字段
- 不引入新的大型抽象层
- 优先修复高风险运行问题
- 每一步都能通过测试独立验证

这意味着本方案不是重构方案，而是**止血 + 收口 + 补齐测试**的工程化修复方案。

---

## 二、修复目标

本轮修复完成后，应满足以下结果：

1. 预配置离线节点不会被健康检查误删
2. 节点断开或禁用隧道后，TCP/UDP 监听循环能真正退出
3. UDP 隧道启动不阻塞节点注册、配置恢复、REST 变更等业务链路
4. usage 统计不会因同名隧道而串台
5. HTTPS 隧道在管理后台可正确展示访问地址
6. 新增自动化测试能覆盖以上风险

---

## 三、修复优先级

| 优先级 | 问题 | 是否影响原有功能 | 是否建议立即修复 |
|--------|------|------------------|------------------|
| P0 | 健康检查误删预配置离线节点 | 是 | 是 |
| P0 | StopTunnel 后 TCP/UDP 循环不退出 | 是 | 是 |
| P0 | StartUDP 阻塞调用链 | 是 | 是 |
| P1 | usage 统计按隧道名单键建模 | 否，但会误导监控 | 是 |
| P1 | HTTPS 访问地址展示不正确 | 有界面影响 | 是 |

建议顺序：

1. 先完成全部 `P0`
2. 再完成全部 `P1`
3. 最后统一补回归测试并跑全量验证

## 四、实施步骤

## Step 1：修复健康检查误删预配置离线节点

### 目标

确保健康检查只清理真正异常失联的在线节点，不误伤合法存在的离线预配置节点。

### 修改文件

- `internal/node/health.go`

### 当前问题

`cleanupDeadNodes()` 当前会把以下节点加入清理列表：

- `Status == offline`
- `LastHeartbeat` 超时

这会把通过后台创建的预配置节点也删掉。

### 最小改动方案

将死节点判定规则改为：

- 仅当 `node.Status == online`
- 且 `node.LastHeartbeat != nil`
- 且 `now.Sub(*node.LastHeartbeat) > heartbeatTimeout`

才加入清理列表。

### 代码层面建议

把当前逻辑：

```go
if node.Status == core.NodeStatusOffline {
    deadNodes = append(...)
} else if node.LastHeartbeat != nil && now.Sub(*node.LastHeartbeat) > heartbeatTimeout {
    deadNodes = append(...)
}
```

改成类似：

```go
if node.Status == core.NodeStatusOnline &&
   node.LastHeartbeat != nil &&
   now.Sub(*node.LastHeartbeat) > heartbeatTimeout {
    deadNodes = append(...)
}
```

### 为什么这是优雅修复

- 不改 `Node` 模型
- 不改 `NodeManager` 接口
- 不影响现有调用方
- 直接恢复原有“预配置离线节点合法存在”的业务语义

### 验证点

- 创建离线预配置节点，等待一轮健康检查后节点仍存在
- 创建在线但超时节点，仍会被清理

---

## Step 2：给隧道运行时增加最小生命周期控制

### 目标

确保 `StopTunnel()` 不只是关句柄，而是能让对应的 TCP/UDP 运行循环退出。

### 修改文件

- `internal/tunnel/registry.go`
- `internal/tunnel/tcp.go`
- `internal/tunnel/udp.go`

### 当前问题

当前 registry 只存：

- `tunnelName -> net.Listener`

这不足以管理完整 runtime 生命周期。

### 最小改动方案

在 `registry.go` 中新增一个轻量 runtime 结构，例如：

```go
type tunnelRuntime struct {
    close func()
}
```

或稍完整一点：

```go
type tunnelRuntime struct {
    close func()
    done  chan struct{}
}
```

然后把 `ListenerRegistry` 从只保存 `net.Listener` 扩展为同时保存：

- `listeners map[string]net.Listener`
- `runtimes map[string]*tunnelRuntime`

### 推荐实现方式

1. `StartTCP()` 启动时创建 `tunnelCtx, cancel := context.WithCancel(ctx)`
2. goroutine 内监听 `tunnelCtx.Done()`
3. `RegisterRuntime(name, runtime)`
4. `StopTunnel(name)` 时：
   - 先调用 runtime 的 `close()`
   - 再注销 listener

对 UDP 同样处理：

1. `StartUDP()` 创建 `tunnelCtx`
2. 所有内部 goroutine 都监听 `tunnelCtx.Done()`
3. `StopTunnel()` 时统一 cancel + close conn

### TCP 需要补的关键退出逻辑

当 `Accept()` 返回错误时，不应直接一律 `continue`，而应先判断：

- `tunnelCtx.Done()`
- `ctx.Done()`
- `errors.Is(err, net.ErrClosed)`

命中则直接 `return`。

### UDP 需要补的关键退出逻辑

当 `ReadFromUDP()` 返回错误时，也应先判断：

- `tunnelCtx.Done()`
- `ctx.Done()`
- `errors.Is(err, net.ErrClosed)`

命中则直接退出主循环。

### 为什么这是最小改动

- 不需要引入新包
- 不需要改变 `TunnelConfigService` 的调用方式
- 不需要修改 API
- 只是在 tunnel 层补足 lifecycle 收口能力

## Step 3：把 StartUDP 改成异步启动

### 目标

让 UDP 隧道启动行为与 TCP 保持一致：监听建立后立即返回，读取循环在后台运行。

### 修改文件

- `internal/tunnel/udp.go`

### 当前问题

`StartUDP()` 目前在函数体内直接进入 `ReadFromUDP()` 无限循环，导致调用方阻塞。

### 最小改动方案

把 `StartUDP()` 改成以下结构：

1. 解析地址
2. 打开 UDP 监听
3. 注册 runtime / adapter
4. 启动 goroutine 运行：
   - 会话清理循环
   - `ctx.Done()` 清理逻辑
   - 主读取循环
5. `StartUDP()` 立即返回 `nil`

### 结构建议

主循环改成：

```go
go func() {
    defer tg.registry.Unregister(tunnel.Name)
    defer conn.Close()
    ...
    for {
        n, addr, err := conn.ReadFromUDP(buf)
        ...
    }
}()
return nil
```

### 注意事项

- `sessions` map 和 `mu` 仍然可沿用现有设计
- 所有 `ConnClosed()` 应与 session 的真实销毁路径保持对称
- 不要把 `conn.Close()` 放在多个路径里重复触发未受控日志

### 为什么这是优雅修复

- 外部调用方无须改动
- 语义与 `StartTCP()` 对齐
- 可以直接解除注册/更新链路阻塞风险

## Step 4：修正 usage 统计主键，避免同名隧道串台

### 目标

确保不同节点即使使用同名隧道，usage 统计也能准确关联。

### 修改文件

- `internal/tunnel/stats.go`
- `internal/tunnel/tcp.go`
- `internal/tunnel/http.go`
- `internal/tunnel/udp.go`
- `internal/api/tunnel_handler.go`
- `admin/src/pages/TunnelsPage.tsx`

### 当前问题

当前统计全都按 `tunnel.Name` 建索引。

### 最小改动方案

新增一个 helper，例如：

```go
func statsKey(nodeID, tunnelName string) string {
    return nodeID + "/" + tunnelName
}
```

然后在写入统计时使用：

- TCP：已有 `node.ID`
- HTTP/WS：已有 `node.ID`
- UDP：找到节点后也有 `node.ID`

在 `Usage()` 组装数据时，同样按：

- `statsKey(n.ID, t.Name)`

读取统计。

前端 `usageMap` 同步改成：

```ts
const key = `${item.node_id}:${item.name}`
map[key] = item
```

渲染时同样使用这个 key。

### 为什么这是最小改动

- 对外 API 响应字段可以完全不变
- 不需要增加数据库字段
- 只是把内部统计关联键从单键改为复合键

## Step 5：修复 HTTPS 隧道访问地址展示

### 目标

让后台 tunnels 页面对 `https` 隧道和 `http` 一样显示正确访问地址。

### 修改文件

- `admin/src/lib/utils.ts`

### 当前问题

当前逻辑只处理：

- `tunnel.type === 'http'`

### 最小改动方案

把判断改成：

```ts
if (tunnel.type === 'http' || tunnel.type === 'https') {
  const scheme = tunnel.type
  const host = tunnel.domain || `${tunnel.name}-${tunnel.node_id}.${base}`
  return `${scheme}://${host}`
}
```

### 为什么这是最小改动

- 只改一个工具函数
- 页面调用方无需改动
- 与已有 HTTP 行为完全兼容

## Step 6：补测试，防止问题再次回归

### 目标

把这次暴露出来的生命周期问题和统计关联问题固定成自动化测试。

### 修改文件

- `internal/node/health_test.go` 或扩展现有 node 测试
- `internal/tunnel/udp_test.go`
- `internal/tunnel/tcp_test.go` 或新增 runtime 退出测试
- `internal/api/tunnel_handler_test.go`
- 必要时补 `admin` 侧轻量测试，若当前前端没有测试框架，可暂时只做手工验证清单

### 必补测试清单

#### 1. 健康检查不误删预配置离线节点

场景：

- 添加一个 `offline` 节点
- 执行一次 `cleanupDeadNodes()`
- 断言节点仍存在

#### 2. 健康检查能清理超时在线节点

场景：

- 添加一个 `online` 且心跳超时节点
- 执行 `cleanupDeadNodes()`
- 断言节点被移除，且回调被触发

#### 3. UDP 启动不阻塞

场景：

- 调用 `StartUDP()`
- 断言函数快速返回

#### 4. StopTunnel 后运行循环退出

场景：

- 启动 TCP 或 UDP 隧道
- 调用 `StopTunnel()`
- 断言不再持续输出关闭错误，或 goroutine 能在有限时间内结束

#### 5. usage 按 `node_id + name` 正确关联

场景：

- 构造两个节点、同名隧道
- 写入不同统计
- 调用 `Usage()`
- 断言返回的两个条目各自命中自己的统计值

#### 6. HTTPS 地址展示

手工验证或前端测试：

- 构造 `https` 隧道
- 断言 `tunnelAccessUrl()` 返回 `https://...`

## 六、实施风险与注意事项

### 6.1 不要扩大改造范围

本轮不建议顺手做以下事情：

- 重写 `ListenerRegistry` 整体抽象
- 改造 `Node` 领域模型
- 改 API 返回结构
- 引入新的事件系统

这些方向未必错误，但会显著扩大改动面，不符合“最小改动”目标。

### 6.2 注意统计与连接计数对称性

在修 lifecycle 时，要特别保证：

- `ConnOpened()` 和 `ConnClosed()` 路径对称
- session timeout、主动 stop、ctx cancel 三条路径都不会重复减计数

### 6.3 注意 StopTunnel 幂等性

`StopTunnel(name)` 最好保证：

- 多次调用不会 panic
- 在未注册 runtime 时可安全返回

### 6.4 注意关闭日志级别

在关闭场景下收到 `net.ErrClosed` 不应打 `ERROR`，否则会制造大量误导性日志。

## 七、最终验收标准

本轮修复完成后，建议按以下标准验收：

### P0 验收

- 创建离线预配置节点后，健康检查不会删除它
- 在线超时节点仍会被健康检查清理
- 启用 UDP 隧道时，节点注册与隧道更新接口能正常返回
- StopTunnel 后不再持续打印关闭错误日志

### P1 验收

- 两个不同节点的同名隧道 usage 统计互不串台
- HTTPS 隧道在后台页面显示正确访问地址

### 回归验收

- `go test ./...` 通过
- 原有 HTTP/TCP/UDP 基本转发功能不回退
- usage API 过滤条件 `node_id/type/status` 仍可正常工作

---

## 八、建议结论

本次修复建议采用“两批提交”的最小改动策略：

1. 第一批只修稳定性和生命周期问题
2. 第二批再修统计准确性与前端展示问题

这样做的优点是：

- 风险可控
- 回归边界清晰
- 便于逐步验证
- 符合当前项目“轻量级、小改动、松耦合”的改进风格

如果后续需要进一步提高长期可维护性，再考虑第二阶段优化，例如：

- 把 tunnel runtime 生命周期抽象得更完整
- 明确统计模型的领域边界
- 为前端补正式单元测试

但这些都不属于本轮“最小改动修复”的必要条件。
