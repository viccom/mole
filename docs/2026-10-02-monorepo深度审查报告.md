## 二、发现清单

### 🔴 A-1 Close-先于-Run 语义洞：仍开着，现已有硬证据

来源：`docs/decisions.md:126` 记录的 MUST-2 修复中发现、**明确未修**的问题。本次复核定性为仍然存在，且找到了客观验收信号。

`decisions.md` 当时写道："回归测试以 rescue 计时器兜底该窗口，测试时长 16-19s 即洞存在的佐证，修后应降至毫秒级。" 实测（`go test -tags p2p .`）：

```
--- PASS: TestCloseConcurrentWithRun              (11.04s)
--- PASS: TestRegisterResponseStillTimesOutBeyond12S (12.00s)
```

仍是 11 秒量级，不是毫秒 → 洞确认存在。

代码事实（`client/client.go`）：

```go
195 func (c *Client) Run(ctx context.Context) error {
196     ctx, cancel := context.WithCancel(ctx)
197     c.cancelMu.Lock()
198     c.cancel = cancel          // ← Close 早于此行执行则 cancel 永久丢失
199     c.cancelMu.Unlock()
...
208     for {
209         select {
210         case <-ctx.Done():     // ← 只看 ctx，不 watch c.closed
211             return ctx.Err()
212         default:
213         }

275 func (c *Client) Close() {
276     c.cancelMu.Lock()
277     cancel := c.cancel
278     c.cancelMu.Unlock()
279     if cancel != nil {         // ← nil 时静默不做任何事
280         cancel()
281     }
282     c.closedOnce.Do(func() { close(c.closed) })   // closed 确实被关了
```

`d4fad6a` 修的是**数据竞争**（cancel 读写无锁），本条是**可达性**：竞争已无，但 Close 落在 198 之前的窗口时 cancel 永久丢失，而 `c.closed` 虽被正确关闭却无人 watch → Run 陷入无限快速重连（transport 已锁存关闭态，Connect 立即失败但循环不退），进程不退出。

**修法**：`for` 循环 select（208-213）增加 `case <-c.closed: return context.Canceled`；`c.sleep` 同样监听 `c.closed`。
**验收标准**：上述两个测试从合计 23s 降至毫秒级。

webssh 是全仓后果最重（远程 shell + SFTP 文件传输）而完全无测试的代码。需澄清：**读下来它的防御是合格的，不是烂代码**——

- `handler.go:277-309` TOFU 主机密钥策略：known_hosts 优先、key mismatch 拒绝、跨连接缓存复用、带 `hostKeysMu` 锁。实现正确。
- `handler.go:311-316` 关于 stdin 写阻塞引发 goroutine + session + stream 连锁泄漏的注释，推理链完整且正确。

问题恰恰在此：`311-316` 那段注释描述的是一条**靠人脑推理走通的死锁消除路径**（超时返回 → readLoop 退出 → `close(done)` → HandleStream select 退出 → `defer session.Close()` 解互锁 → 唤醒阻塞在 `stdin.Write` 的内部 goroutine）。这类不变量没有回归测试，下一个人改 `HandleStream` 的 select 就能无声 reintroduce 该泄漏。**它目前唯一的防线是一行注释。**

**建议**（不做全面补测，只锁两条高收益不变量）：
1. webssh 隧道认证失败/超时路径不泄漏 goroutine（`goleak` 式断言）
2. `readPayload`（`handler.go:546`）的边界与畸形输入

**附带记录（非缺陷，属固有弱点）**：TOFU 缓存 `h.hostKeys` 是**进程内存**且以 `remote.String()`（ip:port）为键 → 进程重启即失忆、同主机换 IP 不交叉验证。这是 TOFU 的定义而非 bug；但若 webssh 面向长期运维而非一次性排障，"首次信任后回写 known_hosts 落盘"收益很大。裁决：列为 P2 待办，不算本次必修。

### 🟠 B-2 wss 控制面中间人敞口：已知已披露，缺的是"没有第三条路"

`client/internal/transport/ws_kcp_dialer.go:37-44`：

```go
if strings.HasPrefix(addr, "wss://") && tlsConfig == nil {
    tlsConfig = &tls.Config{InsecureSkipVerify: true}
    // 配置未启用 tls 时对 wss:// 只能跳过证书校验（兼容自签名部署），
    // 但必须让用户知情：中间人可中继/劫持会话（proof 认证后节点
    // token 不再上线，proof 绑定一次性 challenge 亦不可重放，但流量
    // 机密性仍依赖 TLS——跳过校验即放弃这层防护）
    log.Printf("警告: %s 为 wss:// 地址但配置未启用 tls，已跳过证书校验（存在中间人风险）", addr)
}
```

**这不是新发现**：团队早已知情，注释正确指出 proof 认证已让明文 token 不上线、challenge 不可重放，残余的只是流量机密性，且有用户可见的警告日志。

真正的缺口在**配置面**。全树 grep `ca_file|CACert|RootCAs|ServerName`（transport/config 层）**零命中** → 运维者只有两档：开 TLS 校验（自签名部署直接连不上）或关掉（完全裸奔）。**没有"我只信这一个 CA / 这一个证书指纹"的中间档。**

**必须并入方案 B 的范围**（`docs/plans/2026-09-29-transport-encryption-two-paths.md`，第二拍 `shared/psk` + `shared/noiseconn`）：既然双路径传输加密要做，顺手留一个 CA/指纹 pinning 配置项，比事后补一个选项便宜得多。
⚠️ **风险定性**：若方案 B 只做 Noise 加密而不给 TLS 路径留 pinning，自签名部署会继续走本条 `InsecureSkipVerify` 分支——**等于新加密被老旁路绕过**。这是本报告认为最值得在动手前想清楚的一条。

**同时排掉的（非敞口）**：`easyp2p/mqtt_signal.go:216`、`engine/secure_upgrade.go:85`、`secure/negotiation.go:64` 的 skip 均有对应 PSK pinning / 自签证书设计支撑（`mqtt_signal.go:218-224` 还正确处理了 ServerName 留空会导致 Go TLS 握手直接报错的问题）；`proxy/http.go:226` 是隧道后端本地健康检查性质。

### 🟠 B-3 `easyp2p` / `netx` 是外部血统 fork，不应用第一方尺子量它（并附一条我撤回的怀疑）

`client/internal/p2p/easyp2p/p2p.go` 2708 行、含 **613 行**与 **513 行**两个函数，看上去是全仓最严重的代码质量问题。**结论应当相反**，证据链：

- `client/internal/p2p/crypto/rand.go:21` 注释直写 "Replaces **gonc** secure.GenerateSecureRandomString (signature + behavior **parity**)"

- `client/docs/plans/2026-09-13-p2p-tunnel-integration.md:26` 记录了 tag 与成对文件的人工裁定

**建议动作**：给它一个身份标记——在 `client/CLAUDE.md` 的 p2p 节首注明"fork 自 gonc/p2punch，不按第一方规范审查，除非同步上游否则不重写"，避免后续审查轮反复把它当靶子。

**随机数排查（空）**：`crypto/rand.go` 的 `GenerateSecureRandomString` 用 `cryptoRand.Int`；`math/rand` 只出现在名字自证的 `GenerateSeededRandomString`（确定性）与 `session_secure.go:289,305` 的 HB 填充数（非机密）。无弱随机生成密钥问题。

### 🟠 B-4 `nodeid` 的"Windows 既有基线失败"其实是**被正常化的测试缺陷**

`agents.md:24` 把它写成"已知基线，非回归"，于是无人再看。实测失败原因：

```
--- FAIL: TestDefaultNodeIDFile_UsesHome (0.00s)
    nodeid_test.go:131: defaultNodeIDFile() = "C:\\Users\\viccom\\.moleAgent-client\\node.id"
        want "...\\AppData\\Local\\Temp\\TestDefaultNodeIDFile_UsesHome4148143539\\001\\.moleAgent-client\\node.id"
--- FAIL: TestDefaultNodeIDFile_FallsBackWhenNoHome (0.00s)
    nodeid_test.go:146: fallback = "C:\\Users\\viccom\\.moleAgent-client\\node.id"
        want "...\\go-build4247347020\\b340\\node.id"
```

根因：`client/internal/nodeid/nodeid.go:173` 用 `os.UserHomeDir()`——Windows 上它读 `%USERPROFILE%`；而 `nodeid_test.go:126,137` 设的是 `HOME`，测试自己的注释就写着"os.UserHomeDir 在 Unix 上依赖 $HOME"。**测试是 Unix-only 假设，却跑在 Windows 主力开发平台上。**

真实代价不是红字，而是：`defaultNodeIDFile()` 的 home 解析分支，以及 `nodeid.go:181` 那条"HOME 不可用则回退到可执行文件同目录并打 WARNING"的路径，**在主力平台上从未被执行过**。node ID 决定节点身份持久性，回退错目录会导致节点 ID 漂移/舰队身份错乱，而这条恰恰只有那 2 个测试能覆盖，且它们是红的。

**改判**：按缺陷处理，不按 baseline 处理。修法 5 分钟——`t.Setenv("USERPROFILE", home)`（Windows）与 `HOME` 同时设；或给 `defaultNodeIDFile` 注入 `homeDir func() (string, error)` 使其与 env 约定解耦。
同步更新 `agents.md:24` 与 `decisions.md:33` 的"既有基线"表述。

## 三、明确排除项（记录审查覆盖面，避免后续重复排查）

- **server 分层是干净的**。实测内部依赖图无环、方向一致：
  ```
  cmd → api auth config core crypto dingtalk feishu logging mqtt node ratelimit service storage stun tunnel version
  api     → auth config core crypto dingtalk feishu mqtt ratelimit service version
  service → auth core crypto ratelimit storage tunnel
  tunnel  → core node ratelimit
  auth    → core crypto        mqtt → auth core      node → core
  config  → ratelimit          logging → config      storage → config core crypto
  ```
  **api 零 storage / 零 tunnel / 零 node 具体类型依赖**（🔴5 的修复是真的）；`tunnel` 不向上依赖 service 或 api。仅 `config→ratelimit`、`storage→config`、`logging→config` 三处叶子包引功能包的小倒挂，不值得动。
