## 二、发现清单

### 🔴 A-1 `users:write` 可越权改任意用户密码 → 提权为 admin

**复核状态：主会话已复核（源码逐行确认）**

代码事实（`server/internal/api/user_handler.go:216-231`）：Update 主路径的 `req.Password != ""` 分支直接 `ValidatePasswordStrength → HashPassword → SetPasswordHash`，**无任何主体/客体区分**——改自己的密码与改 admin 的密码走同一分支：

```go
216  if req.Password != "" {
...
227      if err := h.userRepo.SetPasswordHash(id, hash); err != nil {
```

路由注册（`server/cmd/moleagent-serv/main.go:514`）只挂 `users:write`：
```go
514  router.Register("PUT", "/api/v1/users/", userH.Update, "users", "write")
```
（对比 L517 `POST /users/`（AssignRole）挂的是 `users:admin`——授角收口了，改密码没有。）

**根因分析**：SEC-08 修复（resetPassword 子路径加 `users:admin` 门槛）是按**端点**收口，不是按**能力**收口。`password 变更` 是一项能力，存在两个入口（`/password` 子路径 + 主 PUT 路径），只堵了一个。系统性根因：路由层的权限标注（resource × action）与 handler 内的细粒度授权（改他人密码需 admin）没有强制绑定机制，靠人肉逐 handler 补，自然漏。`user_handler_test.go:140` 起的测试只覆盖了子路径，旁路分支零覆盖。

**影响**：任何持 `users:write`（非 admin）的账号，`PUT /api/v1/users/{admin_id}` 带 `{"password":"..."}` 即完成管理员接管（改名+改密组合可再夺用户名）。

**修法**：主路径删除 password 分支（改密只走 `/password` 子路径），或对 `req.Password != ""` 且 `id != claims.UserID` 时要求 `users:admin`。补旁路分支回归测试。

### 🔴 A-2 HTTP 隧道 domain 无跨节点唯一性校验 → 跨租户流量劫持

**复核状态：主会话已复核（grep 零命中 + 索引代码确认）**

代码事实：
- `server/internal/service/tunnel_service.go` 全文件 grep `Domain` **零命中**——服务层的唯一性校验只覆盖隧道名（TCP/UDP 同名，L200-245）与 listen_port 冲突（L251-302），domain 不在任何校验集合内；
- `toValidateView`（`server/internal/core/tunnel_validate.go:25-40`）连 Domain 字段都不传给 shared 校验器；
- 索引侧 `server/internal/tunnel/registry.go:243-245` 后写覆盖（主会话已确认）：

```go
243  if isDomainRoutable(t) {
244      newDomain[t.Domain] = &domainRoute{nodeID: n.ID, tunnelName: t.Name}
245  }
```

- HTTP 网关按 domain 索引取唯一 route（`server/internal/tunnel/http.go:197-215`）。

**根因分析**：domain 是 HTTP 虚拟主机路由键，后加的字段。"隧道唯一性不变量清单"（name、port）建立时它还不存在，加它的人没有把"路由键必须全局唯一"这条不变量扩进清单；写路径与索引各自假设对方保证唯一——索引用 map 后写覆盖、写路径无校验，两边都不兜底。这与 🔴 A-1 同根：**不变量只在建立时刻被检查，没有随字段演进同步**。

**影响**：用户 B（或被控节点经 `tunnel_update` 上行）配置与用户 A 相同 domain 的 HTTP 隧道即可落库并接管该域名全部流量（索引指向谁取决于遍历顺序，后写者赢）。

**修法**：`applyTunnelChangeLocked` 增加跨节点 domain 冲突拒绝（与隧道名校验同法），register 路径天然复用。补冲突回归测试。

### 🔴 A-3 API 响应回显 webssh 凭据，默认配置下即明文

**复核状态：主会话已复核（回显点 + 加密器缺省逻辑逐行确认）**

代码事实：
- 回显点：`server/internal/api/tunnel_handler.go:93`（List 的 `Para: t.Para` 原样入响应）、`:456`（Usage）；`node_handler.go:96/394/442`（节点 List / listTunnels / ListPersisted）同款。主会话已确认 tunnel_handler.go:84-97 结构。
- 默认配置即明文：`server/cmd/moleagent-serv/main.go:68-83`——`auth.tunnel_secret` 为空且 `jwt_secret` 为启动时自动生成 → **tunnelEncryptor = nil**，webssh 凭证明文落库（L82 WARN 明说），此时 API 回显的就是 SSH 密码/私钥原文。
- 即便加密开启：`pushToClient` 下发前解密（`tunnel_service.go:1116-1139`，主会话确认 `decryptWebSSHPara` L1144）→ 客户端 `handleRegister` 原样回传明文 Para → `control.go:985` 直接入内存；`LoadPersisted` 失败时 `ActivateClientTunnels`（`control.go:1064-1068`）路径上明文长期驻留。

**根因分析**："admin/持久化面不接触明文 secret"的设计原则只在两条出口落地：存储层（`encryptWebSSHParaForStorage`，tunnel_service.go:552-561）与推送层（`pushToClient` 解密）。**API 响应序列化是第三个出口**，从未纳入脱敏管线。根因是敏感数据出口没有统一盘点——三个出口各自被单独处理，缺一张"明文凭证可以流向哪里"的全图。

**影响**：任何持 `tunnels:read`/`nodes:read` 的低权限账号可读取可见节点的 SSH 密码/私钥；默认（未配 secret）部署下为明文；加密部署下仍有内存明文窗口 + 响应回显密文可离线爆破（若 secret 弱）。

**修法**：① 响应面统一剥离/打码 webssh Para 敏感字段（复用 `sanitizeNodeForResponse` 思路）；② `handleRegister` 入内存前即对 webssh Para 加密（复用 `encryptWebSSHParaForStorage`）；③ 服务端启动时对"加密器为 nil 且存在 webssh 隧道"给出显著告警。

### 🔴 A-4 客户端内置管理 API 零鉴权 + 仓库内死 token 文件（public 仓库）

**复核状态：主会话已复核（server.go 全文、admin_token.md、git 跟踪状态确认）**

代码事实（`client/builtin/server.go`）：
- L27-35：纯端口写法显式改绑 `0.0.0.0`（注释自述"本服务无鉴权且隧道 Para 含凭据"）；`http.ListenAndServe` 无任何超时参数（L34）；
- 全 handler 无认证中间件；`withCORS` 恒发 `Access-Control-Allow-Origin: *`（L388-399，子代理引用）；
- `client/admin_token.md:1` 存一枚 `mat_` + 64hex 明文 token（主会话确认格式=服务端节点访问令牌 `mat_` 前缀），**全仓 grep 零代码引用**（死文件），且 `git ls-files` 确认已入库（subtree 71dd12a 带入）——而仓库当前为 **public**（decisions.md 2026-10-02 节）；
- 危害面叠加：`POST /api/self-update`（builtin/update.go:101）可触发换二进制+重启 ≈ RCE；AllTunnelStatus 回显 Para 含全部隧道凭据。

**根因分析**：双重半成品叠加。① 内置 HTTP 服务定位是"本机调试面板"，但暴露面（`-http :port` 绑全网卡 + CORS* + self-update 写操作）按"内网服务"实现，鉴权从第一版就缺位（上轮 C-SEC-01 已报未修）；② `admin_token.md` 是一次**未完成的鉴权接线**留下的残骸——token 已生成、中间件从未写，且随手放在 client 根目录随 subtree 进了 public 仓库。若该 token 与生产服务端签发体系同源（`mat_` 正是其格式），则已实质泄漏。

**影响**：局域网内任意主机 / 任意浏览器页面（CSRF + CORS*）可读全部隧道凭据、增删隧道、启停 VPN 子进程、触发自更新。叠加自更新校验链薄弱（🟠 F-6），形成完整 RCE 链。

**修法**：① **立即轮换该 token 并从跟踪中删除 `admin_token.md`**（git 历史内的副本无法抹除，按已泄漏处置）；② 接线 admin token 中间件（缺失即 401），`self-update` 等写操作额外确认；③ 默认仅绑 loopback，CORS 收敛同源；④ `ListenAndServe` 补超时（与 F-10 同修）。

## 三、🟠 应修

### 授权一致性簇

**🟠 F-1 IsAdmin 依赖 JWT 角色快照，撤权最长 24h 不生效**（主会话已复核）
`resource_scope.go:10-25`（主会话逐行确认）：IsAdmin 读 `claims.Roles`（登录时快照，`auth/jwt.go:26-39`），而中间件 RBAC 每请求实时回库（`auth/middleware.go:57`）——两套判定口径。撤权后的旧 JWT 仍可通过低权限端点中间件，且 IsAdmin 仍判真 → 跨租户可见全部节点/隧道（List/Stats/Usage/ListPersisted）、WebSSH 他人节点（webssh_handler.go:89）、给人授角/改角色权限（user_handler.go:123、role_handler.go:89 的 `!IsAdmin` 短路）。
**根因**：授权上下文（claims）承载了"会过期的事实"（roles），而信任边界要求实时事实；两者混用。**修法**：IsAdmin 改实时查库（或中间件把实时 roles 注入 ctx，claims 只携 user_id）。

**🟠 F-2 凭据吊销不断开在线连接**
`access_token_handler.go:110-178`（Delete/Rotate 只动 repo）；校验仅发生在新连接（`service/node_access_auth.go`）。节点经 smux 长活数天，token 吊销/轮换后旧连接保有 register/tunnel_update/p2p 签发全部能力直到下次重连。
**根因**：吊销语义被实现为"拒绝新连接"，而安全语义应是"终结既有授权"。**修法**：吊销/轮换时按 `node.AccessTokenID` 反查在线节点并 RetireNode（复用 🔴6 修复的单入口）。

**🟠 F-3 SSO bind 端点旁路登录限速**
`main.go:483/487`：`/auth/feishu|dingtalk/bind` 为 RegisterPublic 且未包 loginLimiter；`feishu_handler.go:178-196` 校验用户名+密码、失败回 400（即便包了 limiter 也只计 401）。攻击者（可完成 OAuth 的组织内成员）每次 OAuth 换一枚一次性 bind token 即做一次零计数密码猜测。
**根因**：限速挂在"登录端点"而非"密码校验能力"上，与 🔴 A-1 同型（按端点收口漏能力）。**修法**：bind 端点纳入限速器且失败按 401 语义计数。

### 控制面竞态簇

**🟠 F-4 Add+AddSession 非原子，重连风暴下新注册节点被误删**（主会话部分复核）
`control.go:1007`（Add）与 `:1040`（AddSession）之间隔着日志/回调；旧连接清理的 displaced 守卫通过后，`RetireNode`（`node/shard.go:91-102`）Get/Update/Remove 三步非原子；健康检查对 `GetSession` 出错（含 Add→AddSession 窗口的 ErrNodeOffline）直接继续清理（`node/health.go:67-77`）。窗口内新连接完成 Add 会被 Remove 连根删掉，客户端自认在线。
**根因**：注册的两个阶段被当成一个操作引用（调用方视角原子），实现上却是两把锁之间的窗口；displaced 守卫的 TOCTOU 窗口与之叠加。**修法**：会话绑定并进 Add 的分片锁临界区（AddWithSession 原子原语）。

**🟠 F-5 WS 控制面内嵌 http.Server 零超时 → slowloris**（主会话已复核）
`ws_transport.go:64-66`（主会话确认）：`&http.Server{Handler: mux}` 无 ReadHeaderTimeout/IdleTimeout，而 apiSrv/gatewaySrv 均有 10s（main.go:359/427）。**修法**：补齐两超时，与既有两台对齐。

**🟠 F-6 P2P 信令 ACL 只校前缀不绑自身 tokenID（存疑待验）**
`mqtt/broker.go:391-401`：持任一有效 p2p token 可读写任意 `nat-exchange/<任意>`。若 topic 约定为 `nat-exchange/<tokenID>`，tokenID 经 MQTT topics 管理接口（`mqtt:read` 即可）泄露后可窃听/注入他人配对信令。**修法**：OnACLCheck 校验 topic 后缀 == 认证身份的 tokenID。验证前按 🟡 处理。

### 客户端边界簇

**🟠 F-7 自更新校验链薄弱 + 重启跳过 Close → vpn 子进程孤儿**
`builtin/update.go:101-155`（主会话确认 handleSelfUpdate → `UpdateAndRestart`）；go-selfupdater 的 SHA256 校验为空时仅 WARN 跳过（可降级为无校验）、无签名，信任锚仅清单站 TLS；`restart_windows.go:33-65` 拉起新进程后直接 `os.Exit(0)` 不经 `Client.Close()` → `proxy/vpn/sys_windows.go:20-27` 的独立进程组 vnt-cli 变孤儿，新进程 autostart 与之抢端口/设备；`.old` 备份永久残留（全仓无 `CleanupStaleBackup` 调用点）。
**根因**：更新链把"替换二进制"当完整动作，忽略了进程生命周期的交接（Close/清理/备份回收）是更新语义的一部分。**修法**：ed25519/minisign 签名 + 拒绝空 sha256；更新前先 `Close()`；启动时 `CleanupStaleBackup`。

**🟠 F-8 Desktop GetStatus 持 clientMu 跨 vnt REST，GUI 整体冻结**
`cmd/moleagent-desktop/app.go:253-273` 持锁调 `AllTunnelStatus`，后者对每个运行中 vpn 隧道同步发 4 个 HTTP（`client.go:1519-1531`）、每请求 3s 超时（`vnt_client.go:18-25`）→ vnt 无响应时单次 GetStatus 持锁 12s+/隧道，全部 Wails 方法串行阻塞。
**根因**：锁的持有范围跨越了不可控的外部 I/O。**修法**：clientMu 内只取快照、锁外聚合；或 VNTData 改异步缓存。

**🟠 F-9 Desktop 多节点档案共用同一 node.id（存疑待验）**
`app.go:183-202` 的 `clientConfigForNode` 未设 `NodeID/NodeIDFile` → 全部档案经 `nodeid.go:165-184` 的进程级 `~/.moleAgent-client/node.id` 同一身份注册；指向同一服务端的两个档案会触发服务端置换/归属冲突。若"一机一身份"是有意设计请补文档，否则应按档案派生独立 node_id。

**🟠 F-10 dispatchStream goroutine 无 panic recovery**
`client.go:891`（`go c.dispatchStream`）无 recover，而 acceptLoop 有（`client.go:254-261`）。该路径解析不可信服务端输入（含明文/半加密过渡态），单条畸形流 panic 即整进程崩溃，桌面端无 supervisor。**修法**：与 acceptLoop 同款 recover 包裹。

## 五、明确排除项（检查过且判定健康的区域，防后续重复排查）

- **控制面预认证边界**：行长度限制（64KB 认证行 / 1MB 控制消息 / 客户端 1MB 命令行三处有界读）、challenge 一次性绑定、HMAC 常量时间比对、明文 token 不上线、错误文案不区分候选缺失/proof 不符、SEC-13 per-IP 计数锚定
- **登录安全**：dummy bcrypt 均衡四路时序、401 文案不枚举用户名、双维度限速（IP+用户名）+ 全局 16MB body 闸
- **凭据体系**：access token 哈希存储/轮换即失效（新连接）；P2P 信令 token 全生命周期（sha256 落库、恒时比对、24h TTL、签发/吊销互斥、删除级联）
- **enc 开关矩阵**：require 按服务端供给能力判定、TLS/wss 豁免、握手失败绝不回落、未知 enc 版本硬失败——与既有对抗性审查结论一致，无新死角
- **UDP 会话**：claimUDPSession CAS、destroySession 幂等、三路径配额释放完整
- **服务层一致性**：pairingMu 持久基线串行、吊销先于推送、MoveTunnel 同锁回滚含回推；storage ErrNotFound 与真 DB 错误区分、access_token 读改写互斥
- **MQTT broker**：通配符拒绝、节点归属仲裁、rbac nil fail-closed、auth 节流、Publish API 复用同一 ACL 核心
- **客户端 Run 状态机**（A-1 修复后）：c.closed 三处监听、cancelMu、drainTunnelReqs、幽灵会话防护
- **vpn ProcessMgr**：lifecycleMu 串行化、gen 淘汰、rollbackStart、circularBuffer 防护
- **webssh**（补测后）：writeStdinWithTimeout 解互锁链、TOFU mismatch 拒绝、readPayload 边界有测试锁定
- **nodeid/配置持久化**：原子写（tmp+fsync+rename+目录 fsync）、0600 + loadFailed 拒覆盖
- **proto 契约**：命令字/json tag 锁值测试（TunnelWireFields 契约）、encoding/json 标准语义无注入面
- **日志卫生**：全仓扫描无明文 token/secret/psk 入日志
- **工程化纪律**：tag 双前缀纪律、check-tag 守卫、版本注入链三路径一致、E2E 26 场景（认证/加密/MITM/兼容矩阵+抓包验证）质量高、decisions.md 追加式记录与实际高度一致（本轮仅 2 处小漂移，见 C-17）
